## PR-review checkpoint freshness correction — 2026-09-17

The survivor previously bounded rollback only against its last observed authoritative simulation tick. That tick stops during a P2P partition, so an externally retained checkpoint could remain apparently recoverable until a much later real host retirement. The correction records a local monotonic receipt timestamp with each retained checkpoint and requires receipt within four seconds before the trustworthy old-authority retirement boundary. Intentional Leave uses the received frozen-host departure; EOS loss uses the original service-departure event after the existing proof/cohort wait validates it. The later safety wait does not move that event boundary. UTC is not used, packets received after retirement are ineligible, and equal/older checkpoint sequences cannot refresh receipt time.

Deterministic coverage now partitions a two-player active match for five seconds while the healthy host continues, then retires the host through the trusted seam. The survivor still has its pre-partition checkpoint but fails closed without installing authority. Existing recent-checkpoint, intentional Leave, transient recovery, P2P-only denial, corrupt/future/wrong-epoch/stale-tick, former-host return, sequential migration and three-player common-checkpoint cases remain green.

- The prior host pause was caused by requiring the sole client's checkpoint acknowledgement to keep authority live. Healthy hosts now continue through non-host loss; TS-45 reservation, vehicle and connection-generation behavior remain intact.
- Online hosts prove service membership by a unique private EOS member-attribute update every five seconds. The ten-second proof deadline starts at request time. Expiry irrevocably retires the old authority within that membership; delayed responses cannot revive it. P2P-only loss cannot authorize promotion.
- Unexpected host loss requires an explicit EOS departure notification for the established host, fresh survivor membership, a ten-second retirement wait, and exact agreement between the service survivor cohort and the selected checkpoint electorate. Missing evidence fails closed. Explicit authenticated Leave still freezes the departing host immediately. Core election/checkpoint code was not redesigned by this correction.

Client owns detection/timeouts, checkpoint distribution, authenticated transport rebinding and native presentation reset. EOS ownership is coordination only. ## Limits and remaining uncertainty

- No real EOS-connected multi-PC migration, residential NAT/path test, live Locked migration, changed-network former-host restart, or service ownership-notification timing was observed. These remain separate-device acceptance evidence to collect when available.
- The initial implementation required at least two eligible survivors. The approved two-player extension below supersedes that restriction: exactly two players permit one eligible survivor with a safely fenced old authority and a valid external checkpoint. Larger rosters retain unanimous survivor agreement and may deliberately fail recovery after multiple losses.
- Checkpoints are sent every 0.5 seconds; four copies retain approximately 1.5 seconds of boundaries. Selection permits at most 240 simulation ticks of rollback relative to each survivor's observed authoritative state. This is not a wall-clock outage limit or a guarantee that unobserved in-flight state is lossless.
- Default unexpected-loss grace is 30 seconds and agreement is bounded to 20 seconds. Native migration fixtures shorten grace to three seconds; fake-framing tests exercise the default policy.
- The 64,000-byte checkpoint ceiling and acknowledgement lease deliberately stop unsafe continuation when no recent complete state can be retained. Worst-case long-session history, frame cost and eight-player Internet bandwidth have not been profiled.
- Rollback discards post-boundary outcomes. Restored committed state does not replay historical presentation events or add discarded score deltas to restored totals. Presentation-only effects/UI/audio are rebuilt from current authoritative state.
- EOS metadata/promotions are asynchronous and use operation-generation guards/retry for reported failures. Local evidence cannot prove live service liveness or timing.

## Approved two-player migration extension — 2026-09-16

The approved requirement replaces the original minimum of three total players with two. TS-46 and TS-51 descriptions now record that requirement while retaining the larger-roster protections and separate-device acceptance checks. The branch contains current fetched `origin/main` through `58b9d8b`.

### Authority and checkpoint safety

- Exactly two players can elect their sole eligible survivor. The existing Core vote/commit path still advances the epoch once; three-or-more-player checkpoints still require multiple eligible survivors and unanimous agreement.
- The two-player host now needs its client's checkpoint acknowledgement to retain authority. Acknowledgements expire two seconds after checkpoint publication. Monotonic elapsed time expires the lease when a suspended process resumes; delayed/replayed acknowledgements cannot extend it. Unexpected-loss promotion still waits the advertised grace (30 seconds by default, minimum three); intentional Leave freezes before announcing departure.
- The sole replacement selects the newest valid external copy within the existing phase/match/epoch and observed-tick rollback bounds. Missing, corrupt, stale, future or wrong-epoch state creates no replacement authority. Session, player IDs and match generation survive; Ready clears.
- A sole replacement can continue while the former host's disconnected reservation remains. Returning the former host restores it as the same ordinary player and re-establishes the two-player acknowledgement requirement. A later reverse migration advances to epoch 3.
- A two-to-three-player roster expansion must be acknowledged by the original client before it releases the original two-player lease. Accepting the expanded checkpoint retires old two-player copies; selection cannot use them against a currently larger roster. Deterministic partition cases verify that either the original host remains active with the acknowledged larger roster or the isolated original client recovers while the old host is frozen, never both.
- Compatibility bucket `trackstorm-lobby-7` prevents mixing this policy with older two-player hosts that would continue without client acknowledgements. Existing Core epoch, connection-generation, nonce and EOS routing fences remain intact. There is no new state model, service, dependency or Core-to-Client reference.
