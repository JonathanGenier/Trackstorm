## Components changed

- Core transport: `TransportEndpoint` replaces universal string/IP arguments with immutable, bounded Direct-IP or opaque peer/session targets. Address interpretation remains in Client. `TransportCapabilities` and the gateway name expose adapter differences. Peer IDs, messages, delivery, lifecycle and nullable statistics retain their existing semantics. No endpoint serialization or new shared layer was added.
- Client EOS: `IEosP2p`, `EosP2pSdk`, `EosP2pTransport` and `EosPacketAssembly` provide native routing, session admission, framing, bounded processing and cleanup. The existing authenticated `EosSdkPlatform` owns the adapter and disposes it before the platform. Platform Tick stays with the identity owner.
- Online composition: identity service/node, lobby coordinator and session binding create the EOS gateway after compatible membership, transfer the transient access code, authorize native identities and remove closed identity bindings. Compatibility advances to `trackstorm-lobby-2`.
- Player flow: `DevelopmentSession` connects EOS membership to existing lobby authority and the vehicle arena. It displays transport/state and recoverable failures. IP controls remain in explicit Direct-IP development mode. `NetworkTransportNode.Factory` supports explicit gateway composition.
- Direct-IP: GNS translates the new endpoint into its existing native address parser and reports its existing optional features. Call sites and test fakes use the new endpoint factories. Vehicle replication and gameplay authority algorithms were not changed.
- Verification: ten EOS gateway test cases, a Core endpoint test, expanded provider dependency guards, migrated existing networking tests, and optional real EOS P2P host cycles in `EosIntegrationChecks` / `check-eos.ps1 -P2p`.
- Documentation: `features.md` describes ownership, endpoint rationale, admission, reliability, bounds, capabilities, statistics and limitations. `eos-development.md` describes policy, local/export checks and separate-PC testing.

## EOS behavior

The path is authenticated identity -> EOS lobby membership -> EOS P2P -> existing `LobbyNetworkDriver` -> Ready/Start -> existing authoritative vehicle arena -> Return. Core imports neither EOS, GNS, Client nor Godot. EOS does not own gameplay state.

The host validates current membership and compatible session before accepting a native request. A session socket derives from lobby ID and Trackstorm session; independent connection nonces reject old gameplay packets. The host's existing binding checks membership and Locked credentials before authoritative admission. Seven remote slots include pending peers. Connection setup has a 12-second deadline.

Reliable traffic uses EOS ReliableOrdered/channel 0; high-rate traffic uses UnreliableUnordered/channel 1. Payloads up to 64 KiB use bounded fragmentation within the SDK's 1,170-byte datagram limit. Each peer has two fixed assembly buffers. Polling consumes at most 256 datagrams and 256 native callbacks; completed messages are also bounded to 256. Native queues request 1 MiB limits. Overflow/failure closes connections with portable reasons.

Buffers are reused, but completed payload ownership requires one array per message and SDK marshalling can allocate. This is not a zero-allocation implementation. No new package, third-party asset, custom NAT service or relay was introduced. Existing official EOS SDK provenance and license notices remain applicable.

## Risks and handoff

The principal risk is untested real EOS peer establishment and packet interoperability. Single-profile copies share identity and cannot substitute for two devices. Remote disconnect races, session membership timing, residential traversal and sustained native queue pressure need real testing. CGNAT, double-NAT and proxy paths were not observed. Reconnect/resume and host migration remain outside this Story.

The impaired arena failure requires controlled repeated comparison and diagnosis; unchanged main also fails this scenario differently, so attribution remains unresolved. No vehicle-netcode changes were made to mask it. Follow the separate-PC procedure in `eos-development.md`, preserve raw metrics and do not mark Story acceptance complete while required checks fail or remain unverified.
