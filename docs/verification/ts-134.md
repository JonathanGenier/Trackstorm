# TS-134 verification evidence

Scope: TS-134 — Require per-Story verification evidence artifact.

## Implementation

- Updated `docs/workflow.md` so every completed Story must create or update `docs/verification/ts-<number>.md`.
- Defined the report as a historical delivery artifact rather than a current source of truth.
- Required reports to record only actual implementation and verification evidence produced for the Story.
- Required explicit recording of materially changed behavior/systems, commands/results actually run, applicable runtime/manual/native evidence, assumptions, limitations, unresolved risks and unverified areas.
- Required each Story report to be indexed in `docs/verification/README.md`.
- Updated `docs/verification/README.md` to document the naming/indexing convention and historical-evidence boundary.
- No gameplay, runtime, networking, serialization, UI or asset behavior was changed.

## Verification

- Repository instructions and current verification index were inspected before the change.
- The workflow wording was checked for consistency with the existing distinction between current completion checks and historical verification evidence.
- The change is documentation/policy only.
- Story version and Windows export metadata are synchronized with current `main` according to the canonical Story version procedure.
- GitHub CI is expected to provide the required repository build/test/version validation after the PR is created; those results must not be recorded here as passing until they actually complete.

## Limitations / unverified

- No gameplay or Godot runtime validation is applicable because no production/runtime code changed.
- GitHub CI results are not yet available at the time this report was authored and must be treated as pending until the PR run completes.
