## Scope and implementation

Read full Jira TS-145, parent TS-115, and completed TS-140, including their empty comment/child lists. TS-145 alone is implemented. TS-146 two-slot inventory, new items and revised Nitro behavior remain outside scope. Repository routing, workflow, standards, critique, item, simulation, death/respawn, developer diagnostics, recovery and native verification contracts were inspected.

- Registry categories map Missile to Weapon, Wrench/Nitro to Consumable and Oil to Droppable. Default configurable category weights 2/1/1 normalize to 50/25/25.
- Each successful pickup accrues normalized target credit for that stable player, selects a positive-credit category weighted by its credit, spends one allocation unit, then randomly selects a weighted item within that category. Both decisions consume the unchanged TS-140 match-owned SplitMix64 stream.
- Immutable per-player credits, category counts, total count and last selection reside in the existing spawn authority and travel in version-five item publications and nested resume/migration checkpoints. There is no second inventory, spawn authority or RNG. Configuration codec version ten carries the three category tuning options.
- Life changes and suspended reservations preserve history. Restore replaces it at the selected checkpoint without replaying pickups. New matches and new player IDs start fresh. Permanent abandonment removes history after resume rights end. Developer grants and rejected contacts do not count.
- Stats exposes the selected player's credits/counts/total/last category/item. Existing pickup contention, cooldown, use and effect paths remain in their original owners.
- Empty or zero-target categories are excluded, preserving single-item configurations. Remaining targets normalize. Live tuning preserves counts and normalized debt; disabling an allocated category redistributes its residual credit proportionally to the active pool on the next pickup. Decimal rounding residue below 1e-24 is clamped to zero. These tuning choices are documented implementation assumptions; ordinary default decisions follow Jira's specified algorithm.
- No assets or dependencies added. Core remains Godot-free with Client -> Core dependency direction.

## Assumptions, limitations and risks

- **UNVERIFIED:** Authenticated multi-device EOS/Internet/NAT recovery, exported builds, a long multiplayer soak, human competitive-match balance feel, rendered Stats readability and audio. Local native UDP and trusted identity/retirement fixtures are not evidence for those environments.
- **INFERRED:** Real application rematch initialization uses the tested fresh authority/seed path. No manual menu-driven sequence comparison was made.
- The process-kill harness remains general recovery evidence; nonzero category continuation was directly verified in serialized Core and two/three-peer native in-process migration scenarios.
- Global RNG draw order remains shared as TS-140 requires. Another player's pickup advances that stream, but does not change this player's credits, eligibility or probability distribution. Exact future outcomes can depend on global pickup ordering.
- Category/item protocol changes require matching game versions. No backward save migration or mixed-version multiplayer is promised.
- Target changes deliberately affect future allocations; historical counts are retained and are not reinterpreted as if the new targets had applied earlier. Disabled-category debt redistribution is a tuning-edge policy, not a new-match reset.
- Independent engineering PR review and CI are delivery gates, not claimed completed by the runtime critique. No merge was performed.
