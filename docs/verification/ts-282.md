### Exact state logic

- **Natural flight:** tire loss immediately enables input. Until player aerial input is used, neutral frames preserve incoming angular velocity and ordinary linear/gravity motion.
- **Active control:** any nonzero recorded aerial axis adds/counters/redirects angular velocity through the existing bounded chassis-axis control. It arms release hold only when no body contact is present. Releasing one axis while another remains held does not arrest the other existing rotation.
- **Released control:** after control is armed, all three axes zero immediately zero angular velocity on that step and subsequent neutral steps. The existing observed orientation is left untouched. Linear velocity and gravity are untouched. There is no world-up target, orientation snap, automatic landing or new recovery behavior.
- **Contact/reset:** any wheel support, non-wheel body contact (even below crash severity), active crash latch, disabled driving or new vehicle life clears the hold. A neutral unsupported bounce then preserves collision spin. Fresh aerial input can arm another hold once normal control is available. Existing crash-input suppression and delayed recovery remain.
- `AirControlState.ReleaseHoldArmed` reads the existing legacy stabilization X field; production steps write 0/1 there, Y/Z zero. Layout/version/size are unchanged. Snapshot, aggregate, prediction, retune and recovery retain the latch without Client-only memory. TC42 and the retired configuration sliders remain unchanged.

## Assumptions, limitations and risks

- The existing crash latch continues to suppress player input until useful wheel support; this Story preserves its inertia and removes ordinary flight's artificial damping rather than replacing crash recovery.
- Existing absolute safety bounds (65 m/s, 8 rad/s) remain. Contact impulses, supported crash damping and suspension still dissipate energy physically/according to existing arcade tuning.
- Aerial control is now available even in short tire gaps. Holding a driving key that maps to an aerial axis can rotate the vehicle during those gaps, as required. Neutral input no longer holds an attitude; players must counter spin.
- Exact build/configuration matching is required. TC41 network configuration and checkpoints embedding it are intentionally incompatible with TC42; saved key-based local preferences retain unrelated overrides.
- No physical controller ergonomics, continuous human trick-driving session, Internet/EOS multi-device play, export, or second-PC acceptance was performed. Synthetic controller events and local native worlds do not prove those outcomes.
- The window-inspection helper did not expose the hidden playtest window; visual observations used the fixture's actual rendered captures. No desktop input was sent to the user's editor or other apps.
