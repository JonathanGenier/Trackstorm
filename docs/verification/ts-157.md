Evidence collected September 23–24, 2026 on Windows with Godot 4.7.2 .NET and .NET 10. Story branch: `ts-157-jg`. No user-approved scope changes were made.

## Implemented

- Each existing inventory slot owns independent authoritative Nitro charge, initially 100%. Holding use drains the selected resource; release retains charge; subsequent presses reuse it; exhaustion removes only that item. TS-146 slot selection, token/life validation and other item behavior remain in their existing owners.
- Host-consumed input sequences bind remote reliable use requests to their input boundary, including an early reliable re-press. A bounded pending window handles delivery-channel ordering. Clients do not author charge or scoring outcomes.
- Boost increases vehicle acceleration and speed while active. Release/depletion removes the boost and preserves a recovery episode that reduces excess horizontal speed at a bounded rate, without clamping instantly to normal speed. Vertical velocity and ordinary non-Nitro external impulses retain their existing behavior.
- Circus Nitro scoring uses actual authoritative horizontal overspeed, with the existing current K/D multiplier and banking path. It can continue after release and stops at normal speed.
- HUD shows each slot's authoritative percentage, rounded upward while charge remains, plus active boost feedback. Configs exposes consumption rate and overspeed deceleration. Item, vehicle and configuration protocol versions were advanced for the changed state contracts.
- Existing checkpoint/reconnect/migration paths carry exact charge, selection and recovery state. Neutral input clears engagement instead of consuming an offline player's resource. Feature documentation and verification harnesses were updated within their existing ownership boundaries.
- Branch fast-forwarded to current main `4c4b24e` before implementation; a final fetch confirmed main had not advanced. Canonical version is `0.1.46` (Windows `0.1.46.0`). The pre-existing local grass import setting change is excluded from Story delivery.

## Runtime / manual / native evidence

**VERIFIED through executed native scenes and captured output:** The final impaired two-peer Nitro scene reached 44.42 m/s unboosted and 61.55 m/s boosted. Release retained 34.67% charge. After 31 recovery ticks speed was still 60.06 m/s, demonstrating gradual recovery instead of a hard normal-speed snap. Nitro scoring continued during actual post-release overspeed, then stopped after recovery to the normal range. A second press consumed the same partial grant; another release retained it; a third activation depleted it to zero. The other slot's Wrench survived. Host and client converged on item/vehicle/match state.

**VERIFIED through deterministic tests:** Independent charge in both slots, live consumption tuning, death/reset/finished-match cancellation, rejected-step atomicity, immediate prediction release, malformed state rejection, active checkpoint restoration followed by neutralization and reuse, and reliable press arrival ahead of its held/release input sequence.

**VERIFIED through native restoration scenes:** The final reconnect fixture seeded the returning player with 37.5% charge and second-slot selection; all three real UDP resumes restored it exactly without offline draining. Migration fixtures preserved partial charge and restored surrounding score/pending stunt and persistent item state. Process-kill scenes exercised failure/promotion. Partial charge in these recovery fixtures is deliberately seeded through the existing restore API: those scenes do not prove a physical player pressed Nitro immediately before network failure. Active-state round-trip/neutralization is covered separately by Core tests.

## Assumptions, limitations and unresolved risks

- Runtime evidence uses native scripted inputs and observations, not a human driving session or physical gamepad. Motion assertions establish smooth speed recovery; subjective enjoyment, ergonomics and long-session balance are not established by those assertions.
- Default consumption is 20 percentage points/second and excess-speed recovery is 3 m/s². HUD rounds upward so a usable fraction never displays 0%; empty inventory represents exhaustion.
- Recovery tests use local UDP and trusted identity/lease seams; they do not validate authenticated EOS deployment, independent machines, NAT or Internet failure behavior. Initial scores/poses are fixtures in relevant scenes.
- A five-frame main-scene forced shutdown reproducibly reported one leaked RefCounted while asynchronous frontend media was loading. Allowing 120 frames completed cleanly; `check-input.ps1` now allows that loading interval. Abrupt shutdown during loading remains an observed, unresolved limitation outside the Nitro behavior. No warning suppression was added.
- The impaired vehicle run had one large startup reconciliation correction, despite passing its sustained error bounds. Do not interpret that result as a guarantee of invisible correction on all networks.
- State protocols intentionally changed; mixed old/new builds are not supported. No new third-party dependencies or art were introduced; retained images are captures of existing Trackstorm assets.

## Explicitly unverified

Authenticated EOS with real independent identities, separate-PC/WAN/NAT play, exported release gameplay, cross-platform physics, physical controllers, subjective audio/handling feedback, hours-long soak/performance profiling, and every possible combination of abrupt failure during live boost remain unverified. CI on the pushed commit, independent engineering review and human acceptance are separate pending gates at report preparation time. Jira is not marked complete and the branch is not merged by this work.
