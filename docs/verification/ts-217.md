## Corrected behavior and scope

- Acquisition into the selected slot exposes rear armor immediately; acquisition into the other slot stores it. Authoritative selection atomically changes attached `Held <-> RearShield` state at the same reliable revision. Switching away removes cover and presents the newly selected item. Switching back restores the same identity, HP, capability, collision cooldown and damage watermark.
- Both stored and exposed Shields reserve their physical slot. Only the selected pool can intercept a hit, including when both slots contain Shields. Covered rays/projectiles/contacts spend shield HP without duplicate chassis damage; uncovered front/side paths retain normal vehicle damage. Destruction clears the exact occupied slot once.
- Removed the first-use deployment path. Normal use is rejected without a use outcome, consumption, slot release or world deployment. No world-wall geometry, wing expansion or use handler was added. The pre-existing TS-216 host-only wall lifecycle/recovery seam remains; its callers are tests and verification fixtures only. Attached exposure is no longer controlled by that seam.
- Registry default Shield weight changed **0 -> 1**. The existing registry-generated configuration key, immutable spawn weights, category balance and ordinary authoritative acquisition own availability. No new spawn system, key or configuration wire layout was introduced. Explicit saved weight overrides still apply; missing keys/normal defaults resolve to 1. Default/configuration serialization tests cover this value.
- Publications reject attached exposure that disagrees with selected ownership. Existing item protocol 17 carries persistent collision cooldown; resume and migration compose the same item boundary. No independent client hit/exposure authority or pose stream was added.
- Temporary plate geometry and existing damage tuning remain unchanged. Affected item, spawning, vehicle, replication and recovery documentation is synchronized. No dependency or third-party asset additions.

The comprehensive deterministic gate passes, but the broad native suite is **not wholly green**. An isolated source snapshot of unchanged `main` `27d274e`, built separately using the same installed engine/assets/SDK, reproduces these failures:

- Item harness: movable-prop explosion motion assertion. [Story run](ts-217/selection-items.log), [main baseline](ts-217/main-baseline-item_checks.log).
- Salvo harness: current forward-aim marker assertion during a volley. [Story run](ts-217/selection-salvo.log), [main baseline](ts-217/main-baseline-salvo_checks.log).
- Mine harness: native knockback motion assertion after a single correct damage/impulse event. [Story run](ts-217/selection-mine.log), [main baseline](ts-217/main-baseline-mine.log).
- Impaired production pickup inventory harness: both peers acquire all eight items including Shield, but a later full-inventory trial has no matching inventory record. It also fails on main. [Story run](ts-217/selection-pickup.log), [main baseline](ts-217/main-baseline-pickup.log).

These baseline failures were not repaired by expanding TS-217 into unrelated vehicle/weapon behavior. The independent pickup-motion run also fails on both Story and main at the same geometric-validity guard: driver 0, 8 m/s, offset 2.6729002 m, nearest approach 3.0505 m (outside the 3 m pickup radius). [Story motion](ts-217/selection-motion.log), [main motion](ts-217/main-baseline-motion.log). No 180/180 pickup result is claimed for this correction.

Other limitations: temporary plate art; no human-controlled match or controller ergonomics assessment; no exhaustive bank/rollover/grazing contacts, native shield-specific Salvo/mine combinations, long soak, cross-platform or Internet/EOS acceptance. The earlier first-use implementation and its 8.2 critique are [superseded historical evidence](ts-217/initial-implementation.md), not acceptance of the corrected interaction.
