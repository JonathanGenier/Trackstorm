## Controls, runtime ownership and persistence

The [complete control-to-code/runtime mapping](../features/developer-options.md#editable-control-to-runtime-mapping) lists all **59 synchronized controls** individually: 32 vehicle fields, five damage fields, six item fields, five spawn fields, two respawn fields, three match rules and six surface modifiers. It also maps the five local network simulation controls and developer actions. Each gameplay field has a real existing configuration owner and effect evidence; none is an editable placeholder. UI edits commit once through host validation and then use normal simulation, inventory, match and transport paths.

Explicit semantics include proportional live Max HP, clamped steering memory, current in-flight missile speed, future-event lifetime/respawn/pickup delays, restarted item RNG on Seed edit, and a restarted active countdown on duration edit. Finished results and kill targets at/below existing scores cannot be rewritten. Positive subnormal physics values are rejected to prevent division overflow. Give Item requires an empty living host slot. Force Start uses the existing Countdown → Active lifecycle and never persists or changes normal MinimumPlayers.

Schema-one JSONL uses stable keys and independent records. Missing fields use defaults; a targeted top-speed alias migrates; unknown values are preserved without becoming effective; malformed/invalid records are salvaged independently; related valid bounds can apply together. Oversized/future-schema files are not overwritten. Atomic replacement and retryable save failures preserve runtime application. Actions, diagnostics, network simulation and local player preferences are excluded. Accepted tuning still must be explicitly promoted into canonical repository defaults.

Omitted controls are intentional: no drift boost, configurable collision recoil or missile falloff exists; fixed simulation/network cadence, input-history bounds and reconnect grace are not safe live gameplay edits. Arena geometry and projectile capacity remain authored constants. Local camera/audio/display/input preferences remain separate. The feature document records these boundaries and the rule for adding future tunables.
