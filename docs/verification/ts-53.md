# TS-53 local implementation and verification

Evidence recorded on 2026-09-18 for `ts-53-jg`. The live [TS-53 Story](https://jonathangenier.atlassian.net/browse/TS-53) was read before implementation and again during final validation. Its description/criteria were unchanged, with no children, comments or additional approved scope changes. Separate-PC EOS acceptance is still outstanding; this report does not close the Story.

## Resulting implementation

- Core `LobbyAuthority` owns the eight-participant limit, new monotonic identities, pending admission, fifteen-second bootstrap expiry, idempotent repeated connection requests, and separate retained-identity Resume authorization. Disconnected reservations and pending admissions both occupy capacity. Host receive processing serializes the final-slot race.
- Core `HostVehicleSession` prepares the existing complete `ResumeCheckpoint` with current world/configuration/item/spawn/match/prop state and a proposed new spawn. Preparation does not modify the running simulation, create a vehicle, add a live score row or replay gameplay outcomes.
- Client `LobbyNetworkDriver` and `VehicleNetworkDriver` install that checkpoint, reset prediction/history and presentation baselines, acknowledge receipt, commit exactly one vehicle on the host, and publish authoritative activation confirmation. Input remains blocked until that confirmation. Current marker clearance is checked again at commit; ordinary snapshots reconcile any changed spawn pose.
- Existing clients see only committed roster participants. They receive new vehicles through ordinary reliable lifecycle, item/match and world publications. Pending joins are excluded from migration continuation and do not take part in host-loss election while bootstrapping; existing migration behavior is otherwise preserved.
- Public admission has no additional gate. Locked admission uses the existing access-code validation in online integration. `OnlineLobbyCoordinator` advertises authority-derived capacity/eligibility instead of closing discovery on arena entry. Lobby protocol is version six; EOS compatibility is `trackstorm-lobby-13`.
- Interrupted/unacknowledged admission removes its subject binding and pending slot without a vehicle or score row to undo. Failed joins return a bounded public reason, with a one-second rejection delivery allowance before transport closure. Once complete checkpoint receipt is acknowledged and authority commits participation, normal match-long retention applies. A submitted acknowledgement permits a normal resume hint while confirmation is in flight; Core rejects the hint if it never committed.
- `OnlineSessionBinding` accepts a repeated callback for the same authenticated binding without duplicating the participant. Leave/shutdown before complete bootstrap cannot persist a misleading resume locator. Arena teardown releases the fresh-admission callbacks.

## Assumptions and limitations

- Core/session drivers remain owned by the existing serialized host loop; the final-slot tests model both competing arrival orders rather than unsupported concurrent mutation of a single authority object from arbitrary threads.
- Matching builds are required by lobby version six and the new EOS compatibility bucket. Old clients and saved checkpoints from incompatible builds are not supported.
- Bootstrap is bounded to fifteen seconds. Spawn positions may change between proposal and acknowledgement; Core rechecks clearance and ordinary authority corrects the client before normal ongoing synchronization.
- No separate-PC EOS session, residential NAT/relay route, changed public IP, subjective audio/visual quality or long-running Internet soak was verified. Real separate-PC Public/Locked joining is the remaining material acceptance risk.
- The pre-existing `export_presets.cfg` modification was preserved and excluded from TS-53 changes. No dependency, asset, Shared layer, branch switch, PR, Jira transition or requirement change was introduced.
