Implementation date: 2026-09-19. Assigned branch: `ts-70-jg`; synchronized main: `3ea435f`. Jira TS-70 has no children or comments. ## Result and ownership

`Directory.Build.props` owns canonical `MAJOR.RELEASE.PR`, currently `0.0.15`. Release zero is valid. This is an intentional approved baseline, not an increment or reinterpretation of the old four-component `0.0.1.0` value. Core `GameVersion` validates exactly three numeric components and retains exact-equality compatibility. UI, diagnostics, EOS and wire consumers continue to use the same provider. Assembly informational/custom metadata retain the canonical value; .NET assembly/file and Windows numeric resources derive `0.0.15.0` as their four-slot representation.

Normal Stories preserve current main's `MAJOR.RELEASE` and require revision +1. The existing CI `verify` path fetches current main, checks out the PR head and rejects non-ancestor main before evaluating the transition. The `.github/version-transition.json` declaration explicitly binds a dedicated release Story's Jira key and branch to exact source/target versions. It must change relative to main; only next release with revision zero is accepted. Normal Stories cannot change it. A one-time TS-70-only declaration authorizes this exact migration. It is reviewed authorization metadata, never a runtime or build-version source; CI does not authenticate Jira's Story type or approval.

The repository-owned Godot editor/export plugin reads the canonical MSBuild source at editor/export time, supplies packed Godot metadata and overrides Windows export resource versions. It also requests export-option refresh for an already-open editor. Runtime Client startup uses generated Core metadata, never XML. The old `project.godot` version field is removed. `export_presets.cfg` is not edited or staged by TS-70; the user's existing version/company/product edits remain in the working tree. The actual export proves stale preset version fields are overridden while company/product preferences survive.
