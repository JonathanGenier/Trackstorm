## Architecture and acceptance evidence

`GameLoop` accepts one completed `SynchronizedMatchContext` and explicitly exposes Initialization, Countdown, Active and Finished. Trusted composition fixes authority for the owner's lifetime. Non-authority calls cannot initialize, start countdown, advance ticks or report completion. There are no new network commands or Godot dependencies.

Countdown begins at the handoff tick and stores an absolute checked deadline. Only consecutive authoritative ticks can advance the owner. Read-only timer projection cannot activate gameplay. `AllowsGameplay` is true only in Active. Phase revision increments once per accepted transition; rejected/duplicate commands preserve the boundary and revision.

Modes report a validated `MatchOutcome` with a bounded reason and optional winner. Only Active can accept it. Finished freezes the exact state and outcome, rejects competing reports and cannot restart. A new owner represents a new match. Mode-specific scoring and application navigation remain outside the lifecycle.

`GameLoopState` contains the shared transition rules. The existing atomic match evaluation now consumes those rules, while `FirstToTargetMode` reports the existing kill-target end condition. `MatchState.Lifecycle` is a read-only projection, not another mutable owner. Existing score validation, protocol fields, checkpoint restore, roster thresholds, Force Start, countdown cancellation and development combat behavior are preserved.

The new Core gameplay gate is verified as policy, not as end-to-end network input suppression. Separate-PC authenticated EOS, process-kill migration, visual/audio quality and long Internet soaks were not run.
