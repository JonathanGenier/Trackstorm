## Root cause and fix

- `ShieldRequested` used desired selection plus the replacement flag. Missile's independent return path clears that flag while still owning the raised rack. `NetworkVehicleBody.PresentShield` therefore began unfolding the incoming Shield against a fallback pose before its carriage existed. A rendered two-peer native regression on unchanged production code failed with **Shield progress 0.021, rack progress 1.000, no Shield carriage**.
- Shield now requires its installed carriage before unfolding. The existing Missile return continues to own the mechanism through mount folding, rack lowering and complete trunk closure; accepted selection remains pending until normal payload installation.
- The expanded native matrix exposed a second bypass: the incoming Nitro timer could expire while Shield folded and then replace it without full trunk closure. Nitro now enters the existing generic return path while another payload owns the rack, then starts its local 0.60-second visual timeline when the rack is free. Removed the stale replacement pose/deadline shortcuts. Gameplay's authoritative Nitro timer, thrust and fuel rules remain unchanged; a slow outgoing return can delay visible Nitro readiness beyond that gameplay deadline.
- Presentation reseeding now clears Shield carriage progress, shown identity and visibility together with rack/Boost animation memory, then reconstructs accepted state. It does not reset inventory or Shield HP.
- Extended the existing car-rack harness with a focused `-HandoffsOnly` route. The normal car-rack command also invokes it after its existing roster/consecutive-mine checks. No separate animation or inventory authority was introduced.
