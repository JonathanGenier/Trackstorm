# TS-135 verification evidence

Scope: TS-135 — Auto-create PRs for pushed Story branches.

## Implementation

- Added `.github/workflows/auto-create-pr.yml`.
- The workflow triggers on pushes to `ts-*` branches.
- It accepts Trackstorm Story branch names matching `ts-<number>-<suffix>`.
- It targets `main`.
- It checks for an existing open PR before creating anything.
- It confirms the pushed branch is ahead of `main`.
- When needed, it creates exactly one PR with the exact branch name as the initial title and an empty body.
- It uses only GitHub repository data and the built-in GitHub token; no Jira credentials, Jira API access, or Jira integration are required.
- It never merges automatically.
- Updated `docs/workflow.md` so mechanical PR creation may happen immediately on push while Jira/code/verification/CI remain authoritative for review and human acceptance remains required before merge.

## Verification

- Inspected the generated workflow for branch filtering, duplicate prevention, main targeting, ahead-of-main validation, and least-privilege permissions.
- Confirmed the workflow grants only `contents: read` and `pull-requests: write`.
- Confirmed repeated pushes with an existing open PR exit without creating another PR.
- Confirmed the workflow does not read or reference Jira credentials.
- Confirmed the workflow does not contain any merge operation.
- Story version and Windows export metadata are synchronized with current `main`.
- GitHub CI results for this Story are pending until the PR run completes.
- End-to-end push-trigger execution cannot be exercised until this workflow is merged to `main`; a later `ts-*` push is the production acceptance event.

## Limitations / unverified

- GitHub repository Actions settings must permit the built-in workflow token to create Pull Requests. The connected GitHub API did not expose that administrative toggle for verification in this session.
- Existing Story branches created before this workflow is merged will only trigger it after they contain the workflow file (normally by synchronizing with a post-merge `main`).
