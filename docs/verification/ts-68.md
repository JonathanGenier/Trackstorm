Implemented on `ts-68-jg` and synchronized with current `origin/main` at `3ea435f`, which includes TS-65 and merged PR #38 / TS-66. The integrated Story uses canonical version `0.0.1.1`. TS-68 was re-read after its startup-flow clarification; it has no child issues or comments. Current Jira requires Lobby-first startup and treats a local locator only as read-only lookup input until the player explicitly requests retained-session validation. The earlier approved correction also requires version mismatch to preserve that locator because the authoritative reservation remains intact.

## Implemented flow

Application entry presents the Lobby browser first. The existing same-account resume locator now initiates only read-only lobby-ID metadata lookup; startup does not call the provider Resume/JoinLobby path, restore old membership, attach session transport or submit gameplay Resume. Missing or replacement-session metadata clears the stale hint with a previous-session message while EOS remains online. Matching metadata exposes **Check previous session**. Only that explicit action recovers validation membership/routing and sends authenticated `InspectReservation`; `Checking` remains internal progress and never exposes the retained-match prompt. Only an authoritative `Available` result overlays **Reconnect / Leave Match**, and only the subsequent Reconnect choice submits the generation-checked Resume and full checkpoint path. Leave Match retains its existing authoritative confirmation and history semantics. Lookup/validation failures, failed reconnects, unconfirmed releases and game-version mismatches return to the recoverable browser and preserve a retryable hint when the reservation may still exist. Repeated choices cannot start simultaneous operations. In-process transient recovery is preserved.

Core separates occupied/reserved slots from released participant display identities in the same immutable lobby snapshot. Release removes authorization and the occupied slot; the existing vehicle driver removes the suspended vehicle/inventory, while MatchState retains statistics and consumed-life memory. Standings ranks occupied and departed identities together, retaining offline dimming and `--` Ping through results. Additional history pages use Page Up / Page Down. Return clears history with the existing lifecycle. Limits remain eight occupied slots and 256 lifetime match participants.

Lobby protocol version seven carries bounded binary roster/history state and existing JSON controls. Binary names avoid JSON escape expansion at maximum Unicode history size inside the existing migration packet bound. EOS compatibility is `trackstorm-lobby-14`; older peers must update. Locked control-only inspection/abandonment does not bypass the fresh-join access-code gate.

## Limitations and manual acceptance

**UNVERIFIED:** real two-PC EOS restart/rejoin, NAT/routing, provider callback timing and long Internet soak. Fake authenticated EOS datagrams and trusted native identity seams are not equivalent to those checks. The UI choice harness uses deterministic responses; Core release and vehicle cleanup are separately exercised through the production drivers.

Run the following on two PCs with the same new build, for Public and Locked sessions:

1. Start an active match and record the client's identity, vehicle/item state, Kills/Deaths and leaderboard row.
2. Exit/restart that client under the same EOS identity. Verify launch enters the Lobby list, performs no automatic membership rejoin and offers **Check previous session** only after read-only metadata lookup. Select it, then verify the authority check keeps the modal hidden until confirmation. After `Available`, verify the modal appears over the Lobby and gameplay remains unbound until Reconnect is chosen.
3. Choose Reconnect, including repeated activation. Confirm one original identity/vehicle/row and current authoritative state, without a password retry for the retained Locked identity.
4. Repeat departure/restart, choose Leave Match and confirm the client waits for release. Verify the slot can be reused by normal admission, the old claim cannot resume, and name/stats/rank remain offline/dimmed with `--` Ping through results. Check later history pages if more than eight participants have played.
5. Interrupt the release reply, recover and retry. Verify no premature success and an already-released claim resolves cleanly. Exercise host Return/closure while choosing and a short in-process interruption.
6. Confirm Return/new generation clears history. With a mismatched build, confirm gameplay remains unbound and the locator survives; after updating to a compatible build under the same account, confirm the prompt returns and the same PlayerId can reconnect.

Assumptions remain those of the existing locator design: no locator means normal browsing, and a crash before saving the newest generation may produce a stale claim. The host remains the source of truth; unavailable authority cannot be treated as confirmed release. Maximum history preserves the existing 256-participant match bound. History paging currently uses keyboard Page Up / Page Down.
