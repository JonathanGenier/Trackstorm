Story: [TS-322](https://jonathangenier.atlassian.net/browse/TS-322), Epic [TS-321](https://jonathangenier.atlassian.net/browse/TS-321). Branch: `ts-322-pg`. Evidence collected 2026-10-31. ## Result and scope

**Confirmed:** redundant pickup-presentation updates cost CPU and managed allocation. With identical schema-2 benchmark code and accepted newer publications, average `ItemSpawnPresentation.Apply` time decreased **0.1527405 → 0.0208737 ms/call (86.3%)**; allocation decreased **12,067.35 → 3,520.03 bytes/call (70.8%)**. The means are across three processes, each with ten measured batches of 1,000 calls after two discarded warmup batches. Publication construction is excluded.

**Not established:** recovery of the informal 90–110 → 60–70 FPS observation, a historical code regression, or a single cause. Later candidate vehicle/combat samples were often slower; the full-scene comparison is inconclusive, not an FPS win. There was measurable background CPU activity and a confirmed increase in the ordinary application vehicle roster. Neither establishes the cause of the earlier observation.

Human reboot/background-controlled measurements remain **PENDING**. The developer acknowledged the need to adopt a consistent test structure; no human results were supplied. This is the explicit pending-results alternative in the Story acceptance criteria.

Production changes are limited to:

- Cache each pickup's nullable availability and skip unchanged native visibility, particle and label updates. Recovery seeds still refresh all visuals; claim processing remains independent, including a newer claim while already hidden.
- An opt-in `--performance-benchmark` startup entry point, following existing exported verification switches. Ordinary startup behavior is unchanged.

Added a repeatable benchmark scene/PowerShell runner and [human capture procedure](../performance.md). Repaired stale verification fixtures exposed while exercising current gameplay: persistent empty effect owners, current native ground/weapon readiness, automatic practice-car rosters, shield checkpoint capture on quiet ticks, and presentation-aware camera input in the Salvo verification fixture. No physics, damage, balance, authoritative networking/serialization, assets, lighting, shadows, graphics quality or tuning changed. No architectural redesign.

The actual canonical codebase version is **0.2.74**, despite the 0.3.0 milestone wording. Version files, indexes, Jira and PR prose are unchanged by explicit user direction. The normal Story version gate expects 0.2.75; see the verification exception below.

## Reproduction and measurement controls

See [performance.md](../performance.md) for the durable procedure: record machine/build/settings, three 120-second idle/driving/combat trials before and after a manual reboot, unchanged power/display/camera/roster, controlled downloads/background apps, plus 15-minute repeated gameplay and 2–4 human-player runs. Pause cloud sync as part of the recorded background condition if appropriate; do not silently change conditions between trials.

Local environment: Windows 10.0.19045; Intel i5-7600K 3.80 GHz, four logical processors; GTX 1070, OpenGL 3.3 NVIDIA 582.66; approximately 64 GiB RAM; High performance power scheme; SDK 10.0.401; pinned Godot .NET 4.7.2 `ed1daf0bf`. The observed last boot was 2026-10-30 21:21:20 -04:00, not the stale Jira assumption of several days. The existing editor and user applications remained open. No reboot, driver, power, graphics or user-preference change was made.

A nominal three-second process sample observed Firefox consuming 3.12 CPU seconds and OneDrive.Sync.Service 1.58; a subsequent measured 3.11-second interval observed approximately 0.06 CPU cores for Firefox and 0.96 for the benchmark. These are brief observations of varying background activity, not a controlled experiment or attribution of every slow frame. Raw samples are retained.

Current persisted player settings were inspected read-only: windowed 1280×720, FOV 70, camera distance 1.2. A separate project-default probe reported VSync Enabled, frame cap 0 and approximately 144 Hz display refresh **before** the benchmark's overrides. That probe did not load historical gameplay preferences or establish driver-level overrides.

Commands used from the repository root (`$godot` denotes the pinned .NET GUI executable; native check commands used its console counterpart):

```powershell

# Existing Windows preset; final export launched hidden through the GUI binary.

./tools/benchmark-performance.ps1 -GodotPath .godot/ts-322/export/Trackstorm.exe -Exported -Ticks 300 -Runs 3 -Label export-v2-final
```

For the baseline, only `ItemSpawnPresentation.cs` was replaced with its exact base implementation, built, run, and restored in a `finally` block with a source-hash check. No existing user work was discarded. Final candidate runs force-rebuilt after restoration and recorded a different DLL hash. Scene code and parameters were the same. The later export entry-point change does not participate in the direct-scene Debug A/B workloads.

All measured phases used 1280×720, Compatibility rendering, VSync off, no FPS cap, 60 Hz physics, 180 warmup ticks and 300 measured physics ticks (about five seconds) per phase, three fresh processes per implementation. Each process took about 111 seconds overall. Rendering was forced once per process frame with automatic rendering disabled, because hidden Windows windows otherwise skip draws. Results are **offscreen throughput, not presented/displayed FPS**. Images were captured outside measured windows. Neither debugger-attached nor editor-embedded performance was measured.

The runner records environment, logs, counters and raw percentiles; `fpsFromIntervals` is 1000 divided by the mean callback interval. It is not a median FPS or a “1% low.” Nearest-rank p95/p99 frame times, maxima and >33.3/>50 ms counts remain in JSON. Physics/process monitors can be delayed; measured arena-advance CPU time and OS process CPU are distinct, and must not be added blindly.
