### Reproduction and cause

The new native production harness uses two `DevelopmentSession` instances, application loading/ready/start, actual authored oval boxes and native UDP. It initializes cars before the box, then runs native vehicle movement and ordinary production collection. It does not directly grant the tested pickup or call `TryPickup`. Ten sub-tick starting phases are exercised for each speed/offset/player combination.

Before the fix, **152/180** geometrically valid passes acquired an item. At 65 m/s initial speed with a 2.8 m lateral offset, both players missed **all 10/10 attempts**. This reproduces speed-sensitive pickup unreliability, but not the exact human aggregate ~1/20 rate; centered passes were already reliable in this fixture. See [baseline native trace](ts-147/pickup-before.log).

The Client-side candidate gate tested the host's native vehicle body at the previous committed pose. `Host.Step` advanced the authoritative world before Core validated the candidate against the new pose. Both endpoints therefore had to pass the same three-metre 3D proximity test. A valid short crossing could be excluded at the old endpoint, then rejected at the new endpoint on the next tick. The actual normal-speed miss at ticks 4592–4593 logged endpoint distances **3.0067 → 2.9513 → 3.0323 m**; the candidate existed only for the second step, whose final endpoint was outside. Swept closest approach was **2.9507 m**. The native body sample is not evidence of a separate visual-interpolation position. No inventory, random selection, publication or serialization failure was needed to explain this reproduced miss. Source comparison confirms the same dual endpoint gate on current main (`1aa5a46`); this is a shared acquisition defect, not a Proxy-Mine-specific path introduced by its item registration.
