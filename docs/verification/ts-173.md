# TS-173 — Full-roster authoritative match start

## Scope and implementation

Read the complete Jira TS-173 Story before repository inspection (no children/comments). No requirement substitution or Jira change was needed.

- Retained the existing complete application loading/checkpoint barrier: actual resource/scene setup precedes Loaded; installation precedes Synchronized; every connected admitted peer must acknowledge. Disconnected retained identities cannot block the wait or lose reconnect rights.
- Application `Simulation.InitializeMatch` now commits one five-second Countdown through the existing Core Game Loop transition at tick zero. The atomic adapter remains the sole advancing phase owner. Minimum-player and development countdown tuning cannot bypass, cancel, shorten or restart this start. Isolated fixture behavior remains unchanged.
- Fresh admission stays closed through Countdown and opens at Active/GO; retained-player reconnect stays available. Recovery derives initial-release status from its accepted checkpoint phase. A reordered release cannot bypass checkpoint installation or authoritative Active.
- GO is the common tick-300 Active boundary. Existing driving/item gates and the default ten-minute Active timer derive from it. No independent client start timer was introduced.
- Large outlined center-screen numerals, an amber ring/start lights, settling scale transitions and mint GO use accepted host phase/ticks. Local time only animates artwork and clears GO within 0.75 seconds. A delayed Active publication holds 1 and keeps controls gated.
- Added deterministic tests, native UDP start harness, fast-check routing and feature documentation. Story version: `0.1.68`, presets `0.1.68.0`, based on main `1a54d87`.

## Assumptions, limitations, risks and unverified areas

- Readiness is the trusted application contract: selected resources/native scene setup plus installed/acknowledged full checkpoint. It is not remote attestation against modified clients.
- Native multiplayer uses real local UDP sockets and separate physics worlds in one process. Delayed native scene construction materially tests production drivers/worlds, but does not emulate slow disks or separate-process scheduling.
- **UNVERIFIED:** separate PCs/profiles, real multi-user EOS/P2P, residential NAT/Internet, cross-platform starts, hostile clients and long multiplayer soak. Migration uses trusted identity fixtures.
- **UNVERIFIED:** host crash specifically during initial loading. Native migration covers active matches; deterministic recovery tests protect phase/deadline continuity.
- Authoritative ticks/phase define fairness, not simultaneous physical display frames or zero latency. Offline clients cannot display missed numerals; delayed Active keeps controls gated. Reconnect never invents earlier gameplay time.
- **UNVERIFIED:** human-controller feel, subjective audio listening, accessibility review, ultrawide/mobile layouts and very low frame-rate rendering. Render review is 1280×720.
- Existing configurable match duration is retained; default ten-minute budget starts at GO. Development minimum/countdown tuning applies to isolated fixtures, not the fixed application start contract.
- Pre-existing unrelated grass import and environment textures were preserved/excluded. The stale pre-existing export version edit was backed up to OS temp before required main/version synchronization.

No known failing in-scope behavior remains in completed checks. Real-network/hardware limitations remain release-validation risks, not proof of successful remote EOS play.
