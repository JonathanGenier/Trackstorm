## Implementation

- Application composition enables Core `HostVehicleSession` Active-only driving/item-use eligibility. Host input, received remote input, queued/held controls and pending item requests are neutralized outside Active without rewinding acknowledgements. Existing physics, committed effects and simulation ticks continue.
- Client participation requires completed checkpoint/release or activation, an unfrozen current session, and the accepted authoritative Game Loop phase. Neutral prediction/command traffic continues during Countdown and Finished. A local countdown, prediction tick, or newer unreliable movement snapshot never grants Active. A non-Active phase publication neutralizes retained prediction/retransmission controls.
- Reused reliable `TM` phase publications and complete `TR` bootstrap/resume and migration checkpoints. No new phase owner, parallel synchronization stream, protocol schema, provider dependency or Shared layer was added.
- Reused `TE` Synchronized acknowledgements for application reconnects. The host rejects gameplay from an otherwise authenticated resumed binding before checkpoint acknowledgement. Fresh joins retain their existing Activate/committed-roster barrier. Migration clears obsolete readiness sets and reconstructs the same trusted participation policy while restoring phase/deadline/tick.
- Retained existing eight-player/reservation policy, lifetime standings, fresh-admission rejection during Finished, and retained-player resume into final results. Standalone development fixtures may explicitly omit application entry and retain their legacy controls; production `DevelopmentSession` always enables it.
- Added Core and production-driver regression coverage and strengthened native lobby/migration assertions. Updated affected system documentation. No changes to match completion rules, reset/rematch, results navigation, assets or dependencies.
