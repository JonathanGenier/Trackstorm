# Host migration and match rehosting

## Authority and identity

Trackstorm owns the logical session, stable player IDs, `CurrentHostId`, `AuthorityEpoch`, and match generation. The initial host has player ID 1; later hosts keep their existing player IDs. A successful transfer advances the epoch exactly once and preserves the session and match generation. Provider ownership does not grant gameplay authority. Only explicit session creation bootstraps an authority; a provider promotion cannot create one.

`LobbyRestoreState` retains the immutable roster, allocation high-water mark, session clock, authenticated subject bindings, and active-match disconnected reservation deadlines. Subjects are opaque authenticated adapter identities, not credentials or player-supplied wire claims. These mappings are distributed only inside the admitted session. Lobby restore removes the departed host and directly binds every continuing survivor's already authenticated migration transport; it creates no disconnected lobby reservation. Arena restore retains the former host and other disconnected players for authenticated resume. No EOS SDK or Godot types enter Core.

## Detection, freeze and agreement

The hosted coordination boundary is a Cloudflare Worker and one Durable Object per private lease session, using the existing provider-neutral HTTP adapter. The game bundles its public endpoint; the service owns no gameplay/checkpoint state and makes no election decision. See [deployment and authentication](authority-leases.md).

The online composition attaches `SessionMigration` to the existing single lobby receive loop and a [trusted authority lease client](authority-leases.md). A missing connection or two seconds without an accepted checkpoint freezes client gameplay and enters recovery. The initial host holds a ten-second service lease, renewing every two seconds; local permission expires conservatively eight seconds from request start. A healthy host continues simulation during a P2P partition while its lease and independent EOS membership proof remain fresh. The client cannot promote from P2P loss, cached membership or EOS ownership promotion.

Unexpected host loss waits for a fresh service observation of expired authority, then agreement and atomic takeover. It does **not** wait through the former player's reconnect grace or require a delayed EOS departure callback. The candidate acquires the expected old fence only after Core's deterministic agreement. Core commits the next epoch only after successful acquisition; other survivors independently confirm the new holder/epoch before installation. Delayed/stale responses, failed service requests and unavailable fencing fail closed. A paused process checks monotonic permission before its next simulation step and cannot revive an expired epoch.

Healthy clients do not continuously poll Cloudflare. Existing host-loss, authority-pause and agreement state activates one-second trusted lease observation; recovery and completed installation stop it. A new observation period requires a fresh read. Continuing old-host renewal prevents promotion and supplies checkpoint freshness evidence, so cached expiry never replaces the service fence.

Intentional Leave first freezes the old host, announces departure reliably and requests conditional lease release during the existing one-second drain. A missed release may require the remaining lease timeout, but never permits an unsafe early takeover. EOS membership writes remain a separate local liveness check, not the remote atomic authority proof. Metadata/ownership notifications cannot remove unrelated members; explicit departures still update membership and ordinary reconnect state.

When the existing EOS coordinator permanently retires local authority, migration uses that same freeze/departure/release lifecycle before pumping further lease work. The retired epoch can never renew again, including after a delayed response or recovered EOS proof. Release uses the most recent accepted token after any in-flight request completes; failure safely waits for service expiry. Temporary client/P2P loss and recoverable proof delays do not trigger this retirement boundary.

The minimum automatic migration roster is two total players. Election uses the connected roster in the checkpoint, excluding the old host. Exactly two players permit recovery by the sole eligible survivor after the lease and host-loss policy have fenced the old authority. Rosters of three or more still require at least two eligible survivors, the lowest stable PlayerId as candidate, and every eligible survivor's agreement on the same checkpoint digest. Callback order and EOS ownership are irrelevant. Missing candidates, disagreement, or missing required survivors fail after a 20-second agreement deadline. A larger roster cannot use the two-player exception merely because only one client remains reachable.

Peers retain four checkpoints. The sole two-player survivor selects its newest valid externally retained recoverable checkpoint; larger elections select the newest exact checkpoint present in every eligible survivor's offer. Each survivor validates the selection against its own retained bytes and current phase/match before voting. A candidate cannot substitute a newly invented checkpoint. Each process makes at most one attempt per old epoch; failures are terminal for that session attempt. Sequential migrations use a fresh electorate and the next epoch. A disconnected former-host reservation does not pause the replacement. A returning former host is an ordinary client; another client disconnect does not stop the replacement simulation.

Accepting a larger checkpoint retires older two-player copies, and a currently larger roster cannot select a two-player checkpoint. Every connected survivor in the selected checkpoint must agree before takeover. The coordination service does not store or choose the gameplay roster.

## Complete checkpoint

The version-three `TC` migration checkpoint composes the existing complete version-two `TR` resume codecs with authority continuation:

- Stable session, match generation, host, epoch, roster, reconnect generations/reservations, session clock, player allocation high-water mark, private lease session key and former-host retention flags.
- Simulation tick; complete vehicle aggregates, transforms, commanded and observed linear/angular velocity, handling/surface state, HP, damage attribution, collision cooldowns, accepted physical effects, life generations and respawn deadlines.
- Held slots and tokens, active missiles and IDs/lifetime, item revision and the highest token ever issued, including consumed/departed grants.
- Pickup availability, absolute cooldown deadlines, claim identities/tokens, spawn revision and the complete deterministic selector state.
- Match phase/countdown, target, score rows, consumed-life watermarks, winner/finish state and revision.
- Complete live gameplay configuration and its revision, including lobby tuning before arena creation; current native movable-prop poses and velocities as plain numeric records.

Developer Options edits use the existing Core configuration transaction. Migration restores the selected checkpoint's configuration and revision before reconstructing prediction and native bodies; the successor never loads its PC-local overrides over that state. A newer tuning revision observed after the selected checkpoint may roll back with the rest of that boundary only when the authority epoch advances. Within an epoch, lower or conflicting revisions remain rejected. Authored arena geometry remains a matching-build contract. Custom injected test item selectors deliberately cannot be captured as portable authority. Production item selection uses a specified SplitMix64 stream rather than opaque `System.Random` state; restore continues the exact stream without replaying draws. An explicit live seed edit starts a new stream; other tuning edits preserve its position.

The envelope is bounded to 64,000 bytes, versioned, SHA-256 integrity checked, and validated through the existing nested codecs. Complete host construction is validated before a checkpoint is retained. A replacement is built separately before it becomes live authority, so malformed state cannot partially install. The digest detects corruption and identifies agreement; authenticated transport supplies sender trust, not the digest.

## Cadence, retention and rollback

The host publishes a complete checkpoint reliably every 0.5 seconds to admitted peers, in lobby and arena. Four retained copies cover approximately 1.5 seconds between oldest and newest boundaries. The actual payload varies with roster, projectiles, damage memory and lifetime score rows. The checkpoint payload ceiling is 128,000 bytes/second per recipient, or 896,000 bytes/second for seven recipients, before transport framing/retransmission. Pause/running control and ordinary vehicle/item traffic are additional. EOS metadata stores only low-frequency routing/epoch coordination; it never stores gameplay checkpoints.

A healthy connection normally rolls back at most one cadence interval plus delivery delay. Two independent four-second policies bound recovery:

- The **simulation rollback bound** refuses an arena checkpoint ahead of a survivor's observed authoritative tick or more than 240 ticks behind it.
- The **monotonic checkpoint receipt freshness bound** requires the selected external checkpoint to have been received no more than four monotonic seconds before the locally detected gameplay-loss boundary, extended to any later observed old-host renewal. Each retained copy stores its local monotonic receipt timestamp outside the serialized checkpoint. Intentional Leave uses the received frozen-host departure. Unexpected loss uses the first local gameplay-loss timestamp; it does not use a delayed EOS departure timestamp. A changed service renewal token proves later old-host progress, so selection and commit extend this freshness boundary to that observation. UTC and wall-clock time are not used.

Waiting for lease expiry does not itself age a recent crash checkpoint out of recovery. Continued host progress after a long P2P partition does: an isolated survivor cannot roll back a healthy host's later simulation merely because its own observed tick stopped. Packets with equal/older sequences cannot refresh receipt timestamps, and a checkpoint received after the selected boundary is ineligible. A missing recent common checkpoint fails closed; long partitions are not promised lossless recovery.

## Restore and rebind

1. Freeze gameplay and native prop progression while authority is uncertain.
2. Reconnect the EOS star to the deterministic candidate, using authenticated membership and the retained subject map.
3. Select the latest safe external checkpoint for a sole two-player survivor, or exchange digests and collect votes on the newest common boundary for a larger roster.
4. Atomically acquire the expired lease after agreement, confirm its holder/epoch, then commit the next Core epoch once; restore lobby authority with all Ready flags cleared.
5. Reconstruct the new host's existing Core vehicle/item/spawn/match authority. Keep stable vehicle IDs and reserve remote players for fresh authenticated bindings.
6. Rebind surviving clients through the existing reconnect-generation checks. Publish the existing complete resync checkpoint.
7. Discard pending input/use commands, seed acknowledgements, replace snapshot history, reset interpolation/correction/collision feedback, and reseed destruction presentation. Existing surviving Godot vehicle nodes are reused. Props switch to the appropriate host/replica role and restore numeric velocity as well as pose.
8. Resume from the coherent boundary. Provider ownership/metadata is coordinated afterward by the actual EOS owner; it does not decide the gameplay host. Delayed provider snapshots cannot lower the established authority epoch or replace its gameplay host, while ordinary membership and ownership fields can still refresh.

In an active match, the former host may resume its reserved stable player identity as an ordinary client, with no Start/Return, tuning, Force Start or Give Item privilege. Developer controls require current, unfrozen authority; Give Item targets the elected host's stable player ID. Epoch changes discard stale editor drafts. Diagnostics expose current host, epoch, configuration revision and bounded migration/checkpoint counters without credentials. Active-match host Leave retains a match-resume locator and exposes **Resume previous session**, without automatically undoing Leave. Both this action and process restart recover membership by lobby-ID search and ordinary EOS Join, wait for replacement routing instead of connecting back to self, and send Core Resume rather than fresh Join. Retained Locked players do not re-enter a password. The former-host reservation, vehicle, HP, items, lifecycle, score/rank and statistics state survive through the current match without authoritative input while disconnected. Returning requires the same authenticated subject, PlayerId and generation and grants only CLIENT privileges; it never reclaims authority automatically. Disconnected former-host records are removed at Return/session teardown; connected former hosts become ordinary players with normal arena grace in later matches.

In a lobby, host migration starts on intentional or abrupt loss without a reconnect-grace delay, but the existing lease retirement, epoch and agreement fences still decide when authority may safely transfer. The restored lobby omits the former host entirely, preserves the same logical session for authenticated survivors, clears Ready, and carries their active migration connections directly into the new authority. No lobby resume locator or reservation is created. A former lobby host or client returning later follows fresh Public/Locked admission and receives a new PlayerId.

## Stale traffic and one-shot safety

Lobby protocol version four carries host and epoch; all post-admission commands check the authority fence. The version-two `TG` envelope checks session, authority epoch and recipient connection generation before any nested vehicle, item, match or prop codec/event consumer runs. Native connection nonces, subscription generations, monotonic peer handles and coordinator operation generations reject retired connections and delayed callbacks. The version-two `TP` standings diagnostics also fence authority epochs and use the elected host identity. Online compatibility is `trackstorm-lobby-10`: all peers must use the trusted fencing protocol and retention-aware checkpoint/roster schemas.

Restore publishes current item and score state with empty historical event/delta lists. Token high-water marks, missile IDs, life generations, consumed-death watermarks, spawn deadlines and revisions continue from the checkpoint. Pending uses/inputs do not cross the transition. Committed damage is not reapplied when physical continuation effects are restored. Later one-shot outcomes are evaluated by the original authorities and scoped to the new epoch. Rollback can discard outcomes after the selected boundary; it never adds those abandoned outcomes onto the restored totals.

## Failure and verification

Unrecoverable selection, agreement timeout, invalid state, or lost service membership stops gameplay, releases the transport, and exposes a host-migration failure with a usable Leave/menu path. There is no fallback to independent surviving simulations, gameplay server, cloud checkpoint store or manual transfer UI.

The [lease service tests](authority-leases.md) cover atomic fencing and authenticated HTTP separately. Core tests cover exact election agreement, single commit, stale epochs, lobby identity/Ready restore, former-host privileges, compound codec corruption, tokens, selector continuation, pickup revisions, death attribution, respawn and winner/score idempotency. Client tests use production EOS framing with authenticated fake datagrams for lobby/match migration, transient recovery and bounded disagreement. These tests do not establish real EOS connectivity.

`check-migration.ps1 -GodotPath <exe> -Players 2` uses real local UDP peers and isolated native worlds: intentional lobby host leave with immediate former-host removal, normal Ready/Start, active-match authority loss and former-host CLIENT resume, sequential epochs, retained native vehicles, reset prediction and complete gameplay state. `check-migration-processes.ps1 -GodotPath <exe> -Players 2` launches independent Godot processes and forcibly terminates the host after checkpoints exist; the survivor must advance one epoch in the same logical session, removing the former host in lobby or retaining it in arena. Both scripts also support `-Players 3` (the default) to retain multi-survivor and process-kill regression coverage. Both use explicitly trusted local identity and authority-retirement seams, not EOS authentication. The process launcher confirms process exit before writing the retirement marker; UDP timeout itself cannot authorize promotion. Reconnect, lobby, vehicle, combat, spawning, lifecycle and match harnesses remain applicable regressions.

Real EOS multi-PC host loss, service ownership notification timing, Locked migration admission, changed-network former-host restart and long-session Internet behavior require separate-device verification. Never infer these from local UDP or fake-provider success. See [EOS development](../eos-development.md).
