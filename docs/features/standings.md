# Match standings and results

The centered **MATCH STANDINGS** board displays exactly **#, Player Name, Kills, Deaths, Ping** for every current session participant, up to eight. Holding the remappable leaderboard action during Active shows it; releasing hides it. Defaults are physical Tab and controller Back. Finished forces the same board open until leaving the arena/results state. Focus loss and settings suppression use the existing input adapter's release behavior. The overlay does not intercept vehicle controls. Results expose the existing host Return to lobby or client Leave session action in the footer, keeping it reachable at small sizes. Settings render above the board. Local practice has no match ranking or standings board.

## Authority and presentation

`Core.Matches.MatchRanking` is the single deterministic ranking rule: credited kills descending, deaths ascending, then stable PlayerId ascending. The recorded winner is first. Only the current authoritative session roster is ranked; departed players' retained match totals do not occupy current participant rows. Players awaiting their first totals receive zero totals. A departed winner remains identified in the results footer by PlayerId if their session name is no longer available. Disconnect does not rewrite the frozen match result.

`MatchStandingsView` projects the immutable lobby and accepted match snapshots without gameplay mutation. Both the board's `#` and `CombatHud` standing badge consume this projection's Core ranks. Ping, names and local input never affect ranking. There is no new score, lap, ratio or win system. Existing per-match wins remain an internal scoring contract and are not displayed. The small arena status panel retains phase/countdown/target; the standings board owns the player statistics presentation.

`MatchStandings` owns native Godot labels, visibility and layout. Its 1040×520 design scales uniformly inside a 1200×680 safe area, including 640×360 and ultrawide viewports. First place uses a red band, gold text and an explicit LEADER/WINNER label; the local player is marked YOU. Final results also name the winner in the footer. Long names use ellipsis; the full winner name remains in the footer. The frame uses original procedural metal, scratches, rivets and spikes, plus a blank steel sample from the existing project-supplied HUD health texture. No new external assets or fonts are introduced. The TS-28 `Leaderboard Hud.png` and `Leaderboard Scene.png` references guide composition and material treatment, without their example Score/Laps columns or project-wide branding changes.

## Transport-neutral latency

`LobbyNetworkDriver` samples `ITransportGateway.GetStatistics` through authoritative peer-to-PlayerId bindings approximately once per second and publishes a complete presentation-only `TP` version-one payload. The UI sees only stable identities and formatted latency, never SDK objects. Each remote player's latency is host-to-player RTT, including the client's own row; clients do not substitute their own host RTT for other participants. The host has no network hop and displays `--` everywhere. EOS supplies adapter-owned probe RTT through the same interface; Direct-IP supplies native GNS RTT where available. Unsupported or expired samples display `--`. The compact HUD Ping reads the local player entry from this same publication; it does not independently sample the upstream peer. Both use `PingFormatter` for identical numeric values and `--` placeholders, including zero and bounded high latency. The HUD retains descriptive connection lifecycle text while numeric samples are unavailable. Zero milliseconds is valid on loopback.

The payload is at most 132 bytes: version/count, session lifetime, exact lobby revision, arena generation, increasing sample sequence and up to eight unique PlayerId/nullable-millisecond entries. Clients accept only reliable publications from their established host with the exact current roster/session/generation. Invalid counts, identities, duplicate rows, out-of-range values, trailing bytes and stale sequences are rejected atomically. New lobby revisions immediately invalidate old samples; subsequent sampling uses only current connected bindings. Unauthenticated Direct-IP rejoining uses a fresh PlayerId. Authenticated resume retains PlayerId, increments its connection generation and advances the roster revision, invalidating every old sample. Local interruption clears all samples immediately; disconnected reserved rows remain visible with `--`. Samples are not accepted while awaiting reconnect/checkpoint completion. Session replacement constructs fresh diagnostics state. Rebinding sampling never caches by transient peer ID. See [reconnection](reconnection.md).

Samples expire three seconds after acceptance using monotonic presentation time, independent of simulation ticks, including Finished or a stalled simulation. Missing/expired/unsupported samples display `--`. Receipt-based expiry cannot measure time spent queued before arrival without a synchronized remote clock; reliable ordering and sequence validation prevent rollback, but this is diagnostic freshness rather than a clock-synchronized telemetry service. Ping never enters gameplay snapshots, match totals or ranking.

## Verification

Core tests cover eight-player ordering, deterministic ties, changing totals, recorded winners and invalid participant sets. Pure Client tests cover visibility, identity, shared HUD rank, safe unavailable/expired values, rebinds and malformed/stale publications. `check-standings.ps1 -GodotPath <exe> -Visual` runs eight production Direct-IP sessions, synthetic keyboard/controller input, host-published latency, authoritative state fixture changes, all peers' native boards/HUD ranks, persistent Finished results and Return cleanup. It saves active/results images at five viewport sizes under `.godot/standings-checks`. The fixture installs authoritative totals to isolate replication/presentation; `check-match.ps1` separately verifies real missile/ram scoring. Synthetic controller events do not establish physical-controller ergonomics. `check-reconnect.ps1` additionally verifies immediate latency clearing, retained standings identity and fresh samples across three real UDP arena rebinds, rejecting retired publications. Separate-PC authenticated EOS gameplay remains a manual integration check.
