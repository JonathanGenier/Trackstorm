# Match standings and results

The centered **MATCH STANDINGS** board displays exactly **#, Player Name, Score, Kills, Deaths, Ping** for every current-match participant, eight rows per page. Score is the authoritative banked Circus total and retains fractional points when present. Holding the remappable leaderboard action during Active shows it; releasing hides it. Defaults are physical Tab and controller Back. Standalone arena fixtures keep the same board open during Finished. Production Application Flow presents the dedicated [Podium](post-match.md) instead, consuming the same frozen Core results, including the Circus score column. Focus loss and settings suppression use the existing input adapter's release behavior. Page Up / Page Down navigates additional history pages while visible; ordinary vehicle controls are unchanged. The standalone results footer points to ESC for the [Game Menu](game-menu.md). Production Podium owns explicit post-match destinations. Game Menu and Settings render above the board. Local practice has no match ranking or standings board.

## Authority and presentation

Finished presentation uses the same retained authoritative phase/result installed by ordinary publication or reconnect checkpoint. Application driving and item use remain suppressed under the [Game Loop policy](game-loop.md), while the results board and menu stay available. Fresh admission remains closed during Finished; existing retained identities can resume into the frozen result.

`Core.Matches.MatchRanking` is the single deterministic ranking rule: authoritative banked Circus score descending, credited kills descending, deaths ascending, then stable PlayerId ascending. At Circus timer expiry this same order selects the authoritative winner; the recorded winner is first in frozen final results. The authoritative arena roster and departed-history identities include disconnected and intentionally departed participants until Return ends the arena/results lifecycle. Those retained participants keep their names, score rows and ranking eligibility; losing a transport binding does not remove a participant. Players awaiting their first totals receive zero totals. Disconnect does not rewrite the frozen match result or reorder rows by online status.

Each row carries the authoritative roster's `Connected` state. Offline rows dim all five cells to 55% opacity and always display Ping as `--`, even if a diagnostic provider still has a sample. Name, Kills, Deaths and rank remain readable. A valid same-PlayerId resume restores normal opacity and fresh Ping when available, using the same row and authoritative totals. Disconnected vehicles remain vulnerable, so later gameplay can still change their totals/rank before Finished; the disconnect itself never does.

Finished forces the board open without clearing participants, totals, winner or reconnect reservations. Return leaves the results lifecycle, releases disconnected reservations and tears down the arena; the next arena generation constructs fresh per-match scores and ranking. Core owns participant history; the Podium handoff detaches the final roster metadata for presentation without creating another ranking or reservation owner. See [reconnection](reconnection.md) for the Core retention and resume contract.

`MatchStandingsView` projects the immutable lobby and accepted match snapshots without gameplay mutation. During Finished it uses `MatchState.FinalResults.Standings` directly: ranks, participants, banked score and statistics are frozen by Core, not rebuilt from a changing lobby roster. An unavailable display identity gets an offline `Player <id>` fallback until its session metadata is present. Both the board's `#` and `CombatHud` standing badge consume these Core ranks. Ping, names and local input never affect ranking. Existing per-match wins are included in the [results handoff](game-loop.md#final-results-and-application-flow-handoff) but are not displayed on this board. The small arena status panel retains phase/countdown/target; the standings board owns the player statistics presentation.

`MatchStandings` owns native Godot labels, visibility and layout. Its 1040×520 design scales uniformly inside a 1200×680 safe area, including 640×360 and ultrawide viewports. First place uses a red band, gold text and an explicit LEADER/WINNER label; the local player is marked YOU. Final results also name the winner in the footer. Long names use ellipsis; the full winner name remains in the footer. The frame uses original procedural metal, scratches, rivets and spikes, plus a blank steel sample from the existing project-supplied HUD health texture. No new external assets or fonts are introduced. The TS-28 `Leaderboard Hud.png` and `Leaderboard Scene.png` references guide composition and material treatment, without their example Score/Laps columns or project-wide branding changes.

Explicit **Leave Match** releases the reconnect slot while retaining the participant's canonical display identity in Core's `LobbySnapshot.Departed`. Standings ranks the union of occupied slots and departed history using unchanged match scores. Released rows are always offline/dimmed with `--` Ping, even when a replacement fills the slot. The board shows eight rows per page; **Page Up / Page Down** exposes all lifetime participants (up to the match bound of 256), with page count in the header. Rank one retains its leader styling only on its own page. Return clears the history through normal arena teardown. No separate Client history store exists.

## Transport-neutral latency

`LobbyNetworkDriver` samples `ITransportGateway.GetStatistics` through authoritative peer-to-PlayerId bindings approximately once per second and publishes a complete presentation-only `TP` version-two payload. The UI sees only stable identities and formatted latency, never SDK objects. Each remote player's latency is host-to-player RTT, including the client's own row; clients do not substitute their own host RTT for other participants. The host has no network hop and displays `--` everywhere. EOS supplies adapter-owned probe RTT through the same interface; Direct-IP supplies native GNS RTT where available. Unsupported or expired samples display `--`. The compact HUD Ping reads the local player entry from this same publication; it does not independently sample the upstream peer. Both use `PingFormatter` for identical numeric values and `--` placeholders, including zero and bounded high latency. The HUD retains descriptive connection lifecycle text while numeric samples are unavailable. Zero milliseconds is valid on loopback.

The payload is at most 140 bytes: version/count, session lifetime, exact lobby revision, arena generation, authority epoch, increasing sample sequence and up to eight unique PlayerId/nullable-millisecond entries. Clients accept only reliable publications from their established host with the exact current roster/session/generation. Invalid counts, identities, duplicate rows, out-of-range values, trailing bytes and stale sequences are rejected atomically. New lobby revisions immediately invalidate old samples; subsequent sampling uses only current connected bindings. Unauthenticated Direct-IP rejoining uses a fresh PlayerId. Authenticated resume retains PlayerId, increments its connection generation and advances the roster revision, invalidating every old sample. Local interruption clears all samples immediately; disconnected reserved rows remain visible with `--`. Samples are not accepted while awaiting reconnect/checkpoint completion. Migration clears diagnostics and rejects old-epoch publications; the current elected host displays `--`, including when its PlayerId is not 1. Session replacement constructs fresh diagnostics state. Rebinding sampling never caches by transient peer ID. See [reconnection](reconnection.md).

Samples expire three seconds after acceptance using monotonic presentation time, independent of simulation ticks, including Finished or a stalled simulation. Missing/expired/unsupported samples display `--`. Receipt-based expiry cannot measure time spent queued before arrival without a synchronized remote clock; reliable ordering and sequence validation prevent rollback, but this is diagnostic freshness rather than a clock-synchronized telemetry service. Ping never enters gameplay snapshots, match totals or ranking.

## Verification

The retained-match Core scenarios combine real damage scoring, intentional/unexpected disconnect, full-capacity rejection, late resume, continued scoring, timed Circus finish and next-generation reset. Pure presentation coverage checks offline leaders/winners and same-identity resume against unchanged Core ranks. The native reconnect harness also renders a participant with nonzero authoritative fixture totals through 125 seconds offline, resume and final results, checking dimming and `--` Ping.

Core tests cover eight-player score-first ordering, deterministic ties, changing totals, recorded winners and invalid participant sets. Pure Client tests cover visibility, identity, shared HUD rank/score, safe unavailable/expired values, rebinds and malformed/stale publications. `check-standings.ps1 -GodotPath <exe> -Visual` runs eight production Direct-IP sessions, synthetic keyboard/controller input, host-published latency, authoritative score fixture changes, all peers' native boards/HUD ranks and totals, simultaneous pending Circus categories, persistent Finished results and Return cleanup. It saves active/results and unobscured Circus HUD images at five viewport sizes under `.godot/standings-checks`. The fixture installs authoritative totals/pending state to isolate replication/presentation; `check-match.ps1` and `check-stunts.ps1` separately verify real combat and stunt scoring. Synthetic controller events do not establish physical-controller ergonomics. `check-reconnect.ps1` additionally verifies immediate latency clearing, retained standings identity and fresh samples across three real UDP arena rebinds, rejecting retired publications. Separate-PC authenticated EOS gameplay remains a manual integration check.
