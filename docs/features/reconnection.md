# Player Reconnection and Session Resume

## Identity and Authorization

The existing lobby authority owns reconnect reservations. EOS Product User ID authenticates an online subject; Trackstorm SessionId identifies the logical session; PlayerId identifies a player and their vehicle; the transport peer is a temporary connection; and each player has a monotonically increasing connection generation. Neither PUID, IP address nor peer handle becomes a gameplay PlayerId. Client resolves the EOS-authenticated sender into an opaque subject supplied to Core. Core stores that subject privately for the active session; it is never accepted from a gameplay packet or included in the roster.

A resume intent carries the previously acknowledged SessionId, PlayerId and connection generation. The authority requires the same authenticated subject, an unexpired disconnected reservation and a fresh peer. It atomically installs the new mapping, advances the generation and retains the original name and slot. Duplicate live connections, wrong subjects/sessions/generations and expired reservations fail closed. Existing EOS handshake nonces reject old native packets; the `TG` gameplay envelope independently checks logical session and recipient connection generation before any vehicle, item, match or prop decoder runs. Transport handles increase within the gateway lifetime. Core retains only bounded current reservation state, not a growing log of retired connections.

Initial Locked-lobby admission still requires the access code. An already admitted authenticated subject can resume its reserved slot without retaining or resending that code. No custom backend, resume secret or long-term platform credential is introduced. New players remain unable to join an active arena.

## Grace, Leave and Vehicle Policy

Unexpected authenticated transport or membership loss immediately retires input ownership and publishes `Connected = false` and `Ready = false`. The default grace is 1,800 ticks (30 seconds); `LobbyAuthority`/`LobbyNetworkDriver` construction can configure 1–216,000 ticks. The published lobby snapshot carries this duration. A caller advances the session clock at 60 Hz even in the lobby; Core reads no wall clock. At the exact deadline the reservation, subject binding and roster slot expire once. A successful rebind cancels that deadline. Start requires all reserved players to be connected and explicitly ready.

During grace, the host retains the same authoritative vehicle and sends neutral input every step. Pending driving commands and uncommitted item-use requests are discarded immediately. Physics, damage, held items, missiles, pickup cooldowns, death/respawn deadlines and match scoring continue normally; a disconnected vehicle remains vulnerable, can coast or respawn, and receives no invulnerability or rewind. Existing score rows and consumed-life watermarks survive final departure according to match rules. Expiry removes the vehicle and its remaining item ownership.

**Leave session** sends a reliable explicit departure and waits for host acknowledgement, bounded to one second, before closing the gateway. The host removes the slot immediately on that command; it does not start auto-reconnect. If connectivity is already lost and the command cannot arrive, the host releases the reservation at grace expiry. Host departure ends the session; host migration remains unsupported. Unauthenticated Direct-IP sessions keep immediate removal and fresh-ID join behavior. The native reconnect verification harness injects a trusted test identity over Direct-IP solely to exercise the shared production driver.

## Complete Arena Resync

After the lobby authorizes an arena rebind, the existing vehicle driver reconnects the new peer to the suspended vehicle and sends one reliable `TR` checkpoint. It composes the current codecs into a bounded packet below 65,000 bytes: complete vehicle identity/life, tick and input acknowledgement, HP/damage memory, transform and linear/angular velocity, handling/surface state and pending physical effects; all held slots and grant tokens; active missiles; all pickup states and absolute activation deadlines; complete match phase, countdown, target, scores, winner and consumed-life watermarks; and current movable-prop poses/velocities when the native arena is attached.

Version-two checkpoints also include the complete [host gameplay configuration and revision](developer-options.md), cross-validated against vehicle capacity, steering limits, world revision and match target. All components are decoded and cross-validated before installation. The client installs tuning before reconstructing prediction through `PredictedVehicle` at the host's current acknowledgement/tick, with no old pending inputs. The next input is acknowledgement + 1, and prediction advances from the checkpoint tick. Snapshot history is replaced with that one boundary. Remote interpolation cursor, native correction offsets, damage feedback and collision-feedback baselines are reseeded while existing native vehicle nodes retain their identities. Gameplay input stays suppressed until the complete checkpoint is installed. Arena reconstruction after process restart uses the same checkpoint path.

Checkpoint item events and score deltas are empty: current state is restored without replaying historical launches, impacts, repairs, kills or wins. Death presentation seeds current life watermarks without emitting past destruction bursts. [Arena audio](audio.md) also reseeds vehicle, item and match baselines without historical one-shots. Normal later publications retain existing revision, tick, life and grant-token duplicate protection. Other connected players continue using their existing uninterrupted prediction/replication streams.

## Recovery and Restart

The client shows **Connection interrupted**, **Reconnecting**, **Resume succeeded**, **Resume rejected**, **Grace expired** or **Session unavailable**. Re-establishment starts after a one-second delay and retries at two-second intervals when a connection has failed. The entire transport/checkpoint attempt is bounded by the advertised grace; EOS membership recovery has an additional 30-second bound. A refused or unavailable session returns to a usable menu. Explicit Leave cancels recovery. Player Ping switches to disconnected/reconnecting without retaining numeric latency; it remains suppressed until transport, admission and any arena checkpoint are current. Fresh transport handles/nonces own fresh samples, and presentation reads only the current session projection. EOS also expires unanswered latency samples independently of reconnection detection.

`user://session-resume.json` contains only a lobby locator, expected session/host, authenticated user identity, previously acknowledged PlayerId/generation and a local expiry. It contains no access code, platform token or authorization secret. The file is replaced atomically every five seconds while connected and when a new assignment is acknowledged, and retained on application exit for restart. Its two-minute cleanup deadline does not extend the host's grace. Invalid, oversized, expired or account-mismatched files are discarded. Explicit Leave, rejection and failed recovery clear the hint. A write failure leaves in-process reconnect available but can prevent restart recovery. The host always reauthenticates and independently validates any stored claims.

EOS lobbies enable the SDK's JoinLobbyById path so a prior locator can re-establish membership even while arena discovery is hidden. Kicked users require an invite at the EOS layer. This route grants membership only; the existing Core rebind checks grant gameplay access. Restart requires the same EOS identity and an active original host. A crash before the newest generation was saved can leave a stale hint that is deliberately rejected. No cross-session persistence, host rehosting or new-player join-in-progress is provided.

## Verification and Limits

Deterministic Core tests cover grace boundaries/cancellation, identity and generation validation, atomic rebind, Ready reset, old-peer retirement, capacity, repeated cycles, state/checkpoint serialization, prediction baseline, and death/respawn and score continuity. Provider-independent Client tests exercise the production EOS framing over authenticated fake datagrams, repeated lobby/arena recovery, Locked identity authorization, stale stream rejection, restart routing and bounded file validation. They do not prove real EOS remote connectivity.

`check-reconnect.ps1 -GodotPath <exe>` exercises real local UDP sockets and two isolated native Godot worlds: lobby rebind, three arena resyncs, retained vehicle nodes, cleared input/interpolation history, HP/item/spawn/match continuity, and grace expiry. `-Visual` captures the resumed arena under `.godot/reconnect-checks`. Existing eight-peer lobby, item, pickup, death/respawn, match and vehicle checks cover surrounding regressions. The EOS smoke check covers real authentication and lobby/P2P lifecycle with a solo host. Separate-PC EOS interruption, changed public IP, full restart during an active match and long-session Internet soak still require real-device verification using the EOS development procedure.
