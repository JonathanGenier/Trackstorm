# Item Spawn and Distribution

## Acquisition and Authoritative State

Each network arena registers the active map's validated item-marker contract. The [active oval](oval-map.md) supplies 27 markers: five three-lane oval rows, five oval singles and seven infield singles. The same authority, inventory, use, replication and developer grants serve both maps. The retained combat-arena fixture registers eight actual `ItemSpawns` markers extracted by `CombatArena.ValidateScene()`. Core `ItemSpawnAuthority`, owned by `HostVehicleSession`, is registered once before the first world step. Marker IDs and positions come from that validated contract; no additional pickup positions are synthesized. All registered markers start available. After each committed host step, Core sweeps the vehicle center from its preceding authoritative position to its current position against each registered marker's unchanged 3 m sphere. Acquisition does not depend on Godot proxy or interpolated presentation positions. Core also checks living roster membership, available spawn and capacity in the two current-life slots. A life transition or reset is not swept; a replaced/restored boundary cannot reuse an earlier sweep. The host consumes each movement boundary once, before the existing reliable item publication. Remote clients cannot submit a claimed position, recipient or item choice.

An accepted contact selects one item, grants it through the existing `ItemAuthority` two-slot grant API, and records the claimant, grant token, awarded item and next activation tick before publication. Rejected contacts do not advance the selector or consume availability. Core candidates in a host boundary are ordered by ordinal marker ID then vehicle ID, giving simultaneous contestants exactly one winner. This stable tie-break favors the lower vehicle ID for an exact same-tick tie. A full inventory never replaces either item or consumes the pickup; one occupied slot still permits one further pickup. A player remaining in range can acquire again after consuming an item, including within that same committed boundary.

Core advances cooldowns from committed 60 Hz world ticks, after successful vehicle/item simulation. A claim at tick `t` reactivates at `t + CooldownTicks`; clients never activate from a local timer. Claims survive claimant departure or item consumption until the deadline. Lobby return discards the match-owned authority; the next arena starts fresh. Resume checkpoints include this exact state and deadlines; the authority is never restarted on rebind.

## Configuration and Replication

`ItemSpawnConfiguration` defaults to 600 ticks (10 seconds), a three-metre three-dimensional center-to-marker radius, equal within-category Wrench/Missile/Oil/Nitro/Proxy Mine/Salvo/Machine Gun/Shield weights of 1 and seed 34272265 for deterministic fixtures. The immutable weight map must contain exactly the registered identities; weights are nonnegative, at least one is positive, and their sum must fit an integer, cooldown is bounded to 1-216000 ticks, and radius must be finite in (0, 10]. At each fresh application match, the host generates a new seed and stores it in the effective gameplay configuration. Lobby return and rematch create a new host match and therefore a new seed. `HostVehicleSession` owns one `ItemSelectionRandom` SplitMix64 stream initialized from that seed. Category and item decisions both draw from that stream. `ItemRegistry.Categories` defines stable category identities/order and default target weights: Weapon 2, Consumable 1, Droppable 1 (50/25/25). Missile/Salvo/Machine Gun are Weapons, Wrench/Nitro are Consumables, and Oil/Proxy Mine are Droppables. Future items share their registered category's allocation; adding a category extends the same registry, configuration and state maps. `NetworkVehicleArena.SpawnConfiguration` remains an optional pre-entry fixture override. An injected selector supports exact deterministic tests but has no portable checkpoint.

Spawn changes and assigned slots travel together in the existing reliable `ItemPublication`, including absolute activation deadlines and last claim/token/item. Full state is sent when inventory, projectiles, spawn availability or admission changes. Deadlines need no per-tick countdown traffic. Map pickup capacity is bounded to 27 independently of the eight-player limit. The bounded version-eleven codec validates IDs, counts, claim fields and deadline/availability consistency before exposing detached state. The established host, reliable delivery, current arena generation and increasing publication revision remain mandatory. There is no predicted pickup award; latency can delay visible confirmation, and the local view does not reactivate ahead of the host.

## Per-player category credit

`ItemSpawnAuthority` retains an immutable `PlayerItemBalance` per stable player ID after their first successful pickup. A decision adds each effective category's normalized target share, selects among strictly positive credits weighted by those credits, spends one full unit from the chosen category, then draws an item using only that category's configured item weights. Credits are decimal normalized allocation units; decimal division residue below 1e-24 is treated as zero. The category draw uses the existing positive-bound match RNG API; the item draw immediately follows on the same stream. Even a forced category/item consumes its draw. There is no client selection or per-player RNG authority.

For the example Wrench -> Missile -> Oil -> Missile, credits after four pickups are all zero and counts are 1 Consumable / 1 Droppable / 2 Weapon. Consumable is ineligible immediately after Wrench; after Oil only Weapon has positive credit on the next decision. Another player's pickups cannot alter these credits or category odds, although all successful draws advance the shared match stream.

Credit balancing applies to categories, not individual items. At default weights, each Consumable selection independently draws Wrench or Nitro with equal weight; neither item is guaranteed within a fixed pickup count. Consecutive Wrench draws can therefore leave a player without Nitro even while the Consumable allocation meets its 25% target. `HostedLootTests` verifies actual hosted grants into both inventory slots using fresh and older persisted settings, including replication, live tuning and authority restoration.

Category weights are configured through `spawns.category_weapon_weight`, `spawns.category_consumable_weight` and `spawns.category_droppable_weight`. Zero disables a category. A category with no positive item weight is excluded; remaining target weights normalize to one. The complete configuration must contain a usable positive category/item combination. Item-specific weight changes only affect the selected category's internal mix. Tuning does not reset pickup counts or reseed the RNG. Normalized credits survive target changes; if a category becomes disabled/empty, its residual credit is redistributed proportionally across active categories on the next pickup so the active pool remains selectable. This is a host tuning transition, not ordinary match balancing.

History survives death, respawn, transient disconnect, resume and selected migration rollback. Complete reliable item state and nested resume/migration checkpoints carry credits, category counts, total count and last selected item/category for up to eight retained players. Restore replaces history without replaying pickups. A late admission has no history until its first successful pickup; reconnect uses its retained stable ID. Permanent abandonment removes history only when the player has lost resume rights. A true new match creates a fresh authority with empty history. Seed edits restart only the RNG, not history. Rejected pickups and developer grants do not count. The custom fixture selector bypasses balancing and remains nonportable.

The read-only Stats player section exposes this same authoritative history, including zero counts before the first pickup. It is diagnostic state, not a separate analytics service.

## Presentation, Assets and Verification

`ItemSpawnPresentation` instances one non-colliding [Blender carnival stack](../../assets/items/carnival-crate/README.md) per marker: two distressed red wooden crates below, one centred above, with ivory stripes, raised gold stars, brass corners and scalloped circus trim. The approximately 3.09 × 2.85 × 1.77 m stack retains its authored size. On the first physics boundary, `PickupGroundPose` fits its bottom bearing edges to static terrain, aligning the stack to the local slope without a hover animation or ongoing ground queries. Small unevenness is seated into the terrain rather than leaving floating corners. The marker's -Z direction follows travel: measured oval section tangents, north/south underpass, east/west jump and shoreline, and authored infield loop/link headings. This orientation is retained in the map baker and marker scene. The upright billboard label stays above the tilted upper crate and retains that position through cooldown.

Ground fitting moves only the visual. Every authoritative marker position and the three-metre claim sphere remain unchanged. The skill-jump marker carries `pickup_floating=true` in both its authoring scene and baked map; that stack stays at its authored height and skips terrain fitting. The other 26 stacks are grounded. This map-owned presentation flag does not enter Core or replication. Slow supported crossings remain below the elevated skill pickup's sphere; its existing momentum/airborne approach remains the way to acquire it. Shared imported geometry/materials and native LODs serve all 27 markers. Brighter crimson paint and gold/brass preserve the authored wear; a bounded gold ribbon, 16 ambient motes and distance-faded local light provide pickup readability. The entire stack is one generic collectible: the existing authority selects the item on claim, and the local confirmed HUD identifies the result. All three crates and their aura hide together on claim; a `RECHARGING` label remains until confirmed reactivation. No physical colliders or weapon hit targets are introduced. Confirmed collection emits the cosmetic whole-stack smash described below. A use followed by reacquisition updates the local HUD even when there was no intervening empty-slot publication. No inventory identity is attached to vehicle world presentation.

The [crate manifest](../../assets/items/carnival-crate/sources.json) records original geometry, procedural textures and source/export hashes. The approved concepts are retained only in the import-excluded authoring source directory. The [smash manifest](../../assets/items/carnival-crate/smash-sources.json) covers the editable Blender splinter, folded foil and faceted star masters. Legacy weapon/particle provenance remains in `assets/items/sources.json` and the acquired Kenney license. The [arena audio system](audio.md) uses confirmed grant tokens for distinct weapon and Wrench pickup cues; its assets and licenses have a separate manifest.

`PickupSmashProjection` observes the existing reliable spawn claim tokens, once per registered marker and increasing publication revision. A new claim hides the entire intact stack and creates one `CarnivalSmash` at its fitted pose. First admission and explicit recovery seed claim history without replaying old effects; recovery also clears transient debris. Retained claim tokens survive item use and claimant departure, so neither inventory consumption nor disconnect can duplicate or suppress an already accepted burst. Respawn visibility still comes exclusively from Core. The authoritative sphere and swept vehicle-centre test remain unchanged; no crate, weapon or projectile collision nodes are introduced.

Each smash has 72 thick bevelled plank fragments with painted red/ivory faces and bare torn edges, 96 folded gold foil pieces, 12 faceted gold stars, 12 rimmed/embossed coins, 12 solid lightning bolts, 140 curling spark trails and a brief gold flash. Eight shader-animated instance batches plus one flash use shared arena-owned meshes, shaders and textures. The grant token seeds all fragment placement and motion; no individual debris state is networked. A short bounded impulse keeps the default burst just beyond the stack rather than spreading across the road. Cosmetic motion settles solid pieces toward a fitted floor plane, with one ground query for the floating pickup, and never affects physics. Pieces progressively fade, with the owner removed at 12 presentation seconds even during gameplay pause. A newer confirmed world tick ages delayed publications; outcomes already older than the effect lifetime are skipped. Arrival latency can shift visual start time between peers. Recovery restores current availability rather than reconstructing historical debris.

**F1 → Configs → Crates · Local smash VFX** exposes explosion size from 0.5 to 1.5×, default 1. It follows the existing device-local VFX preview convention: immediate, session-only, captured for future bursts, with its own reset and no change to active effects. This preview is not replicated or exported as gameplay tuning; peers using the same preview size reconstruct the same seeded motion, while deliberate local overrides can differ. **Item spawns → Crate respawn time (60 ticks = 1 second)** reuses `spawns.cooldown_ticks`, default 600 (10 seconds), through the existing shared Apply/validation path. Existing cooldown deadlines retain their original tick; edits affect future claims. Neither control changes the intact stack or pickup eligibility/radius. The [Developer Options catalog](developer-options-catalog.md#crate-pickup-tuning) documents the control boundary.

The arena holds at most 54 bursts. Above 27 concurrent bursts, older bursts receive a 0.2-second retirement fade; an extreme same-frame flood evicts the oldest at the hard ceiling. This bounds developer-configured one-tick cooldown pressure. Match teardown frees every owned effect. `check-carnival-smash.ps1 -GodotPath <exe> -Visual` exercises token/recovery behavior, all three crate contact positions at 8/40/65 m/s, native weapon-ray passage, all lighting presets, 60 seconds of synthetic 27-marker publication waves and paused expiry/teardown. Its controlled sweep observations complement actual native driving in `check-pickup-drive.ps1`; they are not physical car playtests. Eight-peer spawn checks verify exact burst totals and identical initial fragment buffers, and native reconnect checks verify no replay after checkpoint installation.

`check-carnival-pickup.ps1 -GodotPath <exe> -Visual` checks the three named crate groups, bounds, shared imported resources, absence of physics nodes, native projectile passage, 120 whole-stack hide/respawn cycles and owner teardown. It checks terrain contact beneath both lower crates, preserved scale/marker centres, facing against measured oval geometry and authored infield guidance, and label clearance. Its rendered views cover 6/16/32 m in all five environment presets, both approaches and every oval/infield location. Frame timings describe the whole rendered map on the executing machine, not an isolated GPU benchmark.

Deterministic NUnit coverage verifies actual registration IDs, single registration, alive/empty/in-range validation, same-tick contention, retry rejection, exact cooldown boundaries, invalid selectors and weights, seeded distribution and complete publication corruption handling. Driver coverage applies the host/trust/delivery/revision guards to spawn-bearing publications.

`check-item-spawns.ps1 -GodotPath <Godot .NET executable>` uses the explicit old combat-map fixture and runs eight actual UDP peers in isolated Godot worlds. Two remote vehicles contest one pickup; every peer verifies one matching claimant/token/item and cooldown. It exercises reactivation, all eight pickup positions, category-weighted registered item awards, occupied vehicles remaining in range without duplicate grants, and 32 further pickup rounds per player with exact replicated history and convergence. After round 16, a live host edit leaves one positive-weight item in each category; all eight players use the new pool without resetting history, committed grants or RNG. The repeated-round fixture clears inventory between rounds without exercising item effects; the item harness covers actual use. `-Impaired` adds 30 ms outbound delay, 5 ms jitter and 2% loss; `-Visual` captures the rendered client. Existing item, lobby and network vehicle checks cover surrounding combat and scene lifecycle. These are local native integration checks, not multi-machine/NAT or long-session performance evidence.

Reconnect and late join keep the live host's stream; replacement authority restores the selected continuation rather than generating a new seed.
