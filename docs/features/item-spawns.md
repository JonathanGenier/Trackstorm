# Item Spawn and Distribution

## Acquisition and Authoritative State

Each network arena registers the active map's validated item-marker contract. The [active oval](oval-map.md) supplies 27 markers: five three-lane oval rows, five oval singles and seven infield singles. The same authority, inventory, use, replication and developer grants serve both maps. The retained combat-arena fixture registers eight actual `ItemSpawns` markers extracted by `CombatArena.ValidateScene()`. Core `ItemSpawnAuthority`, owned by `HostVehicleSession`, is registered once before the first world step. Marker IDs and positions come from that validated contract; no additional pickup positions are synthesized. All registered markers start available. The host's Client adapter detects proximity using native vehicle proxies and scene markers, then Core rechecks the committed vehicle position, living roster membership, available spawn and available capacity in the two current-life slots. Remote clients cannot submit a claimed position, recipient or item choice.

An accepted contact selects one item, grants it through the existing `ItemAuthority` two-slot grant API, and records the claimant, grant token, awarded item and next activation tick before publication. Rejected contacts do not advance the selector or consume availability. Contacts in a host boundary are deduplicated and ordered by ordinal marker ID then vehicle ID, giving simultaneous contestants exactly one winner. This stable tie-break favors the lower vehicle ID for an exact same-tick tie. A full inventory never replaces either item or consumes the pickup; one occupied slot still permits one further pickup. A player remaining in range can acquire again after consuming an item, including within that same committed boundary.

Core advances cooldowns from committed 60 Hz world ticks, after successful vehicle/item simulation. A claim at tick `t` reactivates at `t + CooldownTicks`; clients never activate from a local timer. Claims survive claimant departure or item consumption until the deadline. Lobby return discards the match-owned authority; the next arena starts fresh. Resume checkpoints include this exact state and deadlines; the authority is never restarted on rebind.

## Configuration and Replication

`ItemSpawnConfiguration` defaults to 600 ticks (10 seconds), a three-metre three-dimensional center-to-marker radius, equal Wrench/Missile/Oil/Nitro weights and seed 1 for deterministic fixtures. The immutable weight map must contain exactly the registered identities; weights are nonnegative, at least one is positive, and their sum must fit an integer, cooldown is bounded to 1-216000 ticks, and radius must be finite in (0, 10]. At each fresh application match, the host generates a new seed and stores it in the effective gameplay configuration. Lobby return and rematch create a new host match and therefore a new seed. `HostVehicleSession` owns one `ItemSelectionRandom` SplitMix64 stream initialized from that seed. Category and item decisions both draw from that stream. `ItemRegistry.Categories` defines stable category identities/order and default target weights: Weapon 2, Consumable 1, Droppable 1 (50/25/25). Missile is a Weapon, Wrench/Nitro are Consumables, and Oil is a Droppable. Future items share their registered category's allocation; adding a category extends the same registry, configuration and state maps. `NetworkVehicleArena.SpawnConfiguration` remains an optional pre-entry fixture override. An injected selector supports exact deterministic tests but has no portable checkpoint.

Spawn changes and assigned slots travel together in the existing reliable `ItemPublication`, including absolute activation deadlines and last claim/token/item. Full state is sent when inventory, projectiles, spawn availability or admission changes. Deadlines need no per-tick countdown traffic. Map pickup capacity is bounded to 27 independently of the eight-player limit. The bounded version-seven codec validates IDs, counts, claim fields and deadline/availability consistency before exposing detached state. The established host, reliable delivery, current arena generation and increasing publication revision remain mandatory. There is no predicted pickup award; latency can delay visible confirmation, and the local view does not reactivate ahead of the host.

## Per-player category credit

`ItemSpawnAuthority` retains an immutable `PlayerItemBalance` per stable player ID after their first successful pickup. A decision adds each effective category's normalized target share, selects among strictly positive credits weighted by those credits, spends one full unit from the chosen category, then draws an item using only that category's configured item weights. Credits are decimal normalized allocation units; decimal division residue below 1e-24 is treated as zero. The category draw uses the existing positive-bound match RNG API; the item draw immediately follows on the same stream. Even a forced category/item consumes its draw. There is no client selection or per-player RNG authority.

For the example Wrench -> Missile -> Oil -> Missile, credits after four pickups are all zero and counts are 1 Consumable / 1 Droppable / 2 Weapon. Consumable is ineligible immediately after Wrench; after Oil only Weapon has positive credit on the next decision. Another player's pickups cannot alter these credits or category odds, although all successful draws advance the shared match stream.

Credit balancing applies to categories, not individual items. At default weights, each Consumable selection independently draws Wrench or Nitro with equal weight; neither item is guaranteed within a fixed pickup count. Consecutive Wrench draws can therefore leave a player without Nitro even while the Consumable allocation meets its 25% target. `HostedLootTests` verifies actual hosted grants into both inventory slots using fresh and older persisted settings, including replication, live tuning and authority restoration.

Category weights are configured through `spawns.category_weapon_weight`, `spawns.category_consumable_weight` and `spawns.category_droppable_weight`. Zero disables a category. A category with no positive item weight is excluded; remaining target weights normalize to one. The complete configuration must contain a usable positive category/item combination. Item-specific weight changes only affect the selected category's internal mix. Tuning does not reset pickup counts or reseed the RNG. Normalized credits survive target changes; if a category becomes disabled/empty, its residual credit is redistributed proportionally across active categories on the next pickup so the active pool remains selectable. This is a host tuning transition, not ordinary match balancing.

History survives death, respawn, transient disconnect, resume and selected migration rollback. Complete reliable item state and nested resume/migration checkpoints carry credits, category counts, total count and last selected item/category for up to eight retained players. Restore replaces history without replaying pickups. A late admission has no history until its first successful pickup; reconnect uses its retained stable ID. Permanent abandonment removes history only when the player has lost resume rights. A true new match creates a fresh authority with empty history. Seed edits restart only the RNG, not history. Rejected pickups and developer grants do not count. The custom fixture selector bypasses balancing and remains nonportable.

The read-only Stats player section exposes this same authoritative history, including zero counts before the first pickup. It is diagnostic state, not a separate analytics service.

## Presentation, Assets and Verification

`ItemSpawnPresentation` builds one floating, rotating, non-colliding pickup per marker from the already acquired CC0 Kenney Weapon Pack rocket geometry. The existing rusty emissive pickup material, local light and native `GpuParticles3D` make it stand out from arena props. The rocket is a generic pickup marker: the item is selected on claim, and the local confirmed HUD identifies the result. Active models and particles hide together on claim; a `RECHARGING` label remains until confirmed reactivation. A use followed by reacquisition updates the local HUD even when there was no intervening empty-slot publication. No inventory identity is attached to vehicle world presentation.

Provenance and license remain in `assets/items/sources.json` and the acquired Kenney license. The [arena audio system](audio.md) uses confirmed grant tokens for distinct weapon and Wrench pickup cues; its assets and licenses have a separate manifest.

Deterministic NUnit coverage verifies actual registration IDs, single registration, alive/empty/in-range validation, same-tick contention, retry rejection, exact cooldown boundaries, invalid selectors and weights, seeded distribution and complete publication corruption handling. Driver coverage applies the host/trust/delivery/revision guards to spawn-bearing publications.

`check-item-spawns.ps1 -GodotPath <Godot .NET executable>` uses the explicit old combat-map fixture and runs eight actual UDP peers in isolated Godot worlds. Two remote vehicles contest one pickup; every peer verifies one matching claimant/token/item and cooldown. It exercises reactivation, all eight pickup positions, category-weighted distribution of all four items, occupied vehicles remaining in range without duplicate grants, and 32 further pickup rounds per player with exact replicated history and convergence. The repeated-round fixture clears inventory between rounds without exercising item effects; the item harness covers actual use. `-Impaired` adds 30 ms outbound delay, 5 ms jitter and 2% loss; `-Visual` captures the rendered client. Existing item, lobby and network vehicle checks cover surrounding combat and scene lifecycle. These are local native integration checks, not multi-machine/NAT or long-session performance evidence.

See [reconnection and session resume](reconnection.md) for authenticated grace, rebind and checkpoint semantics.

Host [Developer Options](developer-options.md) updates the existing spawn authority. Native observation and Core claims use the accepted pickup radius; future successful claims use the current cooldown and weights. Existing activation deadlines remain unchanged. A Seed edit resets the match-owned portable SplitMix64 stream without consuming a draw. Other tuning edits preserve its position. The generated match seed travels in the replicated configuration and resume checkpoints; host-migration checkpoints additionally retain the exact match stream state. Reconnect and late join keep the live host's stream; replacement authority restores the selected continuation rather than generating a new seed.
