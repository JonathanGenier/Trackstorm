# Development Lobby and Session Flow

## Behavior and Controls

Selecting **Developer fallback: Direct-IP / LAN** opens **Host Game** and **Join Game by address** with display-name and numeric address entry. Explicit transport launch arguments also select this fallback. The default `127.0.0.1:27020` is for same-machine development. For LAN hosting, enter the host's local interface address or `0.0.0.0:27020`; clients enter the host's reachable LAN address and port. IPv6 endpoints use brackets. The host listener and joining clients use the existing GameNetworkingSockets gateway. Invalid endpoints return a visible error; admission failure, connection timeout or host loss returns to Host/Join with a diagnostic. Settings remain available from the main menu and the [ESC Game Menu](game-menu.md), suppressing only local gameplay input while open.

The authoritative roster contains one host and at most seven clients. The [3D joined Lobby](match-entry.md) displays sanitized names and host/local/ready markers on vehicle nameplates. Non-hosts explicitly choose **Ready / Not Ready**. The host sees **Start**, which requests Start without a separate host readiness requirement. Core requires a lobby phase, one through eight connected players, every connected non-host ready, and an exact match between admitted peers and the transport connection roster. Lobby disconnects are removed immediately, so no disconnected reservation can block Start. A solo host can Start directly.

One accepted start publishes the shared arena phase, selected map and generation over reliable ordered delivery. The [application match-entry flow](match-entry.md) loads the authoritative Old Map or New Map and completes a checkpoint acknowledgement barrier before starting the existing authoritative vehicle/prediction loop. Clients cannot start or end an arena, even by submitting those intents directly over the transport. The host Return lifecycle command, used by Podium and development harnesses, is a match-completion transition: it tears down each arena, retains connected session identities, and resets every ready flag. The arena has [authoritative first-to-target scoring](matches.md), including countdown and a Finished result. Finishing freezes scores and enters the [Podium](post-match.md), retaining the arena; host Return remains the lobby transition. Host Rematch applies Return cleanup and publishes a fresh generation that every peer loads and synchronizes. A later start constructs a fresh arena without reconnecting. **Quit to Main Menu** remains available in the lobby through the existing cleanup gate. During gameplay, **Leave to Main Menu** is in the ESC Game Menu. Podium exposes its own Main Menu and Quit actions plus host Rematch, Return to Lobby and End Match; the last two use the same existing authoritative Return semantics. Both use the existing session Leave path: an individual client disconnects; an online host initiates the existing migration flow, while direct-IP sessions without authenticated migration close on host departure. Quit and the window close request use that path and await session and online-membership cleanup before normal tree teardown. Failed online cleanup keeps Quit retryable rather than bypassing it.

## Core Ownership and Wire Invariants

Fresh Join and Resume intents carry the canonical [game version](game-versioning.md). Core checks exact equality before any admission allocation or rebind, including Direct-IP. A distinct reliable rejection supplies the hosted version for a clear local mismatch message; rejected connections receive no authoritative roster or gameplay bootstrap.

`Core.Sessions.LobbyAuthority` owns the transport-sender mapping, monotonically assigned player IDs, capacity, readiness and lifecycle mutations. Identity one belongs to the initial host; `CurrentHostId` identifies later elected hosts and `AuthorityEpoch` fences their traffic; remote IDs are never reassigned to another player within the session. An authenticated resume retains its existing ID. Names are not identities and duplicate names are permitted. Names retain Unicode letters/digits, hyphen and underscore, collapse whitespace, discard control/markup/directional characters, and truncate to 24 Unicode scalars without splitting surrogate pairs. Empty results become `Player`. Player IDs represent this development session only, not authenticated accounts or reconnect credentials.

`LobbySnapshot` validates and copies a complete immutable roster. `LobbyReplica` accepts publications only from the established host, for the same session and recipient identity, with increasing revision and nondecreasing arena generation. Client UI renders this state directly. `LobbyCodec` uses `TL` magic, version eight and a message-kind byte, bounded to 30,000 bytes. Roster state uses binary primitives and strict UTF-8 names so up to 256 lifetime participants fit inside migration checkpoints; control messages retain depth-eight bounded JSON. State messages carry session, host identity, authority epoch, revision, arena generation, phase, selected map, recipient ID and all player records including connected state, connection generation and former-host retention, plus departed display identities without reservation authorization. Ordinary client intents carry no target player ID; ownership comes from the transport sender. Resume claims include the prior assignment and are separately checked against the authenticated subject. Session, generation and phase guards reject stale ready/start/return commands. Versions, JSON shapes, roster identities and canonical names are validated before publication.

Client `LobbyNetworkDriver` routes these reliable intents and snapshots through the existing `ITransportGateway`; `DevelopmentSession` owns controls, transport-node lifetime and arena presentation. There is one receive consumer per session: the lobby driver dispatches vehicle payloads to the existing vehicle driver only while the arena is active. Core remains engine-independent and the dependency is strictly `Client -> Core`.

## Vehicle Integration and Disconnects

The lobby starts a new `HostVehicleSession` with its admitted sender-to-player mapping. `JoinPlayer` creates vehicles with the existing stable player IDs and available spawn slots. Remote input still routes by actual sender, never a client-selected vehicle. Lobby phase changes are reliable; existing redundant vehicle inputs and 20 Hz snapshots remain unreliable. Arena generations advance on every start so delayed vehicle packets from a prior match cannot initialize the new prediction/history. Early world snapshots arriving before arena construction may be discarded; subsequent snapshots initialize prediction through the existing bounded input-history path.

In the lobby, explicit departure and unexpected authenticated loss both remove the Core player, subject binding and readiness immediately; a returning identity performs a fresh join. In an arena, intentional and unexpected departure both reserve identity and vehicle until explicit authenticated abandonment or Return, with Ready reset. A valid retained player may resume the same arena; eligible new players may join automatically through the active-match bootstrap described below. Online host departure in either phase follows [host migration](host-migration.md), with no reconnect-grace delay and bounded failure when trusted fencing or agreement cannot be established. Return to lobby retains connected sockets but clears all disconnected match reservations and reconstructs vehicle authority, prediction, interpolation and collision proxies on the next start.

Arena teardown explicitly disposes `VehicleNetworkDriver`, detaching arena admission/migration callbacks and releasing match authority, predictions, items, publications and native observers. This local disposal never closes the session gateway or changes reservations; the existing Core Return/Leave rules own that decision. Connected identities, map selection, tuning and session history remain with their session owners. Application Flow can retain the immutable [final-results handoff](game-loop.md#final-results-and-application-flow-handoff) before teardown, and the next arena reconstructs every match-scoped owner through loading/sync.

## Fresh admission during an arena

Public active matches admit eligible new players automatically. Locked / Private matches use the existing EOS access-code prompt and host-side credential validation, then the identical automatic admission path. No host approval, admission queue or second credential gate exists. Core makes the final decision: eight occupied roster slots total, including disconnected retained players and pending bootstrap participants. Host receive processing serializes competing requests, so only one arrival can reserve the final slot. A duplicate request from the same authenticated connection returns its existing identity; a retained subject must use Resume and cannot claim a new slot.

An arena admission first reserves a new monotonic PlayerId and publishes its provisional assignment to that recipient. Existing clients see the committed roster until activation; other pending participants are omitted. Vehicle authority constructs the existing complete `TR` checkpoint from current gameplay, with a proposed new vehicle at an available arena marker. This preparation does not insert a simulated vehicle, add live score totals, consume a pickup or emit spawn/gameplay events. The checkpoint includes existing vehicle transforms/velocities, HP/lives/respawn deadlines, configuration, inventory, projectiles, pickup deadlines, match phase/countdown/totals and native props. Historical item events and score deltas are omitted.

The new client suppresses gameplay input until it validates and installs the checkpoint and the authoritative Game Loop phase allows participation. It replaces prediction/input history and remote snapshot history, and reseeds interpolation, collision feedback, destruction and audio baselines. The reliable Activate acknowledgement precedes gameplay input, which stays suppressed until a subsequent host roster publication confirms committed activation. The host accepts it only for a pending connection with a prepared checkpoint, rechecks match eligibility and current marker clearance, and commits exactly one vehicle through normal simulation authority. A marker occupied while the checkpoint was in transit is reselected through the same clearance rule; normal authoritative snapshots reconcile that pose. Existing vehicles, scores, timers and item state continue uninterrupted. Existing clients receive the new vehicle through ordinary reliable roster/lifecycle and snapshot publication.

Pending admission has a fifteen-second host timeout. Disconnect, Leave, timeout, failed checkpoint send, unavailable spawn or terminal/closing state releases its identity binding and roster capacity without a vehicle or score-row cleanup obligation. Rejections carry a bounded public reason and close the rejected transport after a one-second delivery allowance. Clients return through the existing recoverable session failure path. Once the complete checkpoint has been acknowledged and authority commits participation, subsequent loss follows normal match-long reconnect retention. After submitting the checkpoint acknowledgement, a client may retain its ordinary resume locator even while host confirmation is in flight; Core rejects that hint if the acknowledgement never committed. Before complete checkpoint installation there is no resume hint. Pending participants are excluded from migration continuation because they have no committed vehicle. Rejected identities are never reused.

Arena Waiting, Countdown and Active phases may admit; Finished, frozen/retiring authority, full capacity and unavailable arena authority reject. Discovery metadata follows authoritative eligibility and occupancy, rather than closing solely on arena entry. EOS membership capacity may reject earlier. Resume remains a distinct authenticated claim to an existing retained PlayerId.

## Verification and Intentional Limits

Core NUnit tests cover eight-player capacity, duplicate/invalid/retired IDs, sender-targeted ready/unready, connected-roster and host-only start validation, return/reset/repeat, removal in both phases, name boundaries and Unicode sanitization, malformed state payloads, replica ordering and stale command guards. `check-lobby.ps1 -GodotPath <Godot .NET executable>` runs eight production session UIs over actual UDP in isolated Godot viewport/physics worlds. It exercises UI Host/Join and ready actions, matching names/IDs on every peer, non-host start rejection, one-command synchronized start, stable vehicle identities, two arena cycles, ready-client removal/rejoin, in-arena retention, fresh eighth-player admission after gameplay starts, interrupted-bootstrap cleanup/retry, retained-slot overflow rejection and host-loss cleanup. `-Visual` renders the host and saves lobby/arena screenshots and evidence under `.godot/lobby-checks`.

The lobby harness uses eight real sockets and eight isolated native worlds in one process. Separate-process vehicle checks remain in `check-network-vehicles.ps1`; transport impairment/capacity tests remain in `check-transport.ps1`. These local checks do not establish cross-machine firewall/NAT behavior, cross-platform compatibility, hostile Internet security, long-session soak stability or subjective controller ergonomics. Transitions converge through reliable delivery; peers are not promised to load/render on exactly the same wall-clock frame, and initial entry uses the bounded loading/checkpoint barrier. The separate [match countdown](matches.md) runs on authoritative ticks after arena entry. The host-controlled return is an intentional development limitation, not a full competitive match service.

The session also supplies the [match standings](standings.md) projection and host-published per-player latency. Lobby revision/session changes invalidate diagnostics immediately; current roster membership determines board rows.
During the arena, that roster includes every committed disconnected participant through Finished/results. Unless explicitly abandoned, their slots remain reserved. Abandonment releases only the slot and authorization, retaining display identity and authoritative match totals for standings; offline state affects dimming and Ping, not ranking eligibility. Return exits results and releases disconnected reservations before the next match generation constructs fresh scores.
See [reconnection and session resume](reconnection.md) for authenticated match-long retention, rebind and checkpoint semantics.

[Developer Options](developer-options.md) uses current session authority to gate tuning and actions. The host loads its separate persisted gameplay overrides when creating a new session; subsequent arenas and migration successors inherit authoritative session tuning, and joining clients initialize from the host's reliable configuration. Force Start readies the local host and invokes normal lobby Start before arming the arena's ordinary countdown with a one-shot solo override. Other admitted players still must be connected and ready.
